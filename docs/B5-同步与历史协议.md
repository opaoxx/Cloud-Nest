# B5 同步与历史协议（范围与验收草案）

基线为 B4 收尾提交 `4c71ca1`。本稿供评审，依据[整体方案第 9 节与阶段 4 验收](<../云盘 SaaS 项目技术方案书（混合架构版）.md>)、[后端 B5 路线](后端设计方案书.md#13-分阶段实施与验收)和[数据库扩展设计](数据库设计方案书.md#6-分阶段扩展字段)。

## 1. 交付范围

| 后端能力 | 本阶段需要交付的结果 |
| --- | --- |
| 变更日志 | 同账号目录变更与事件在同一事务提交，客户端可按序追赶；回收、恢复和清理具有明确的同步语义 |
| 一致性快照和设备游标 | 新设备用固定快照建立基线，后续按页拉取并确认；离线过久、设备需要重建或快照失效时有明确恢复路径 |
| 内容替换 | 在同一文件 ID 下用 `expected_revision` 条件替换已校验的内容；冲突后仍能保留双方内容 |
| 最小历史引用 | 被替换内容按原方案默认保留 30 天，计入逻辑配额；到期清理释放配额，仍有引用的对象受 GC 保护 |

整体实施顺序仍是桌面单向备份先于双向同步。B5 后端以隔离客户端验收上述协议；Wails、Flutter 的手动传输、桌面监听与本地落盘，按整体方案各自阶段验收。历史浏览界面、移动端常驻同步、分享与传输协议实验沿用原规划。

## 2. 变更日志和可恢复的同步基线

**写路径。** 目录创建、上传发布、秒传、重命名、移动、回收、恢复、内容替换和永久清理批次均纳入日志覆盖清单，包含后台标记 `PURGING` 和分批推进 `PURGED` 的同步语义。先锁所属账号，再按原锁序校验目标、版本和祖先，写入业务结果、递增 `users.change_seq`，并追加 `change_events`。失败一起回滚。收藏和访问偏好沿用原语义。文件和目录以稳定的 `entry_id` 识别，移动和改名通过事件交付更新后的父目录、名称及版本；有后代的目录按祖先关系处理，评审时定稿事件载荷和子树边界。删除事件保留墓碑，历史事件可在原条目墓碑清理后继续读取。

**快照与增量。** 快照内容与快照截止序号读取自同一个一致性视图。多页交付绑定同一份有界快照，过期后重新取得完整快照。基线建立后，从快照截止序号之后拉取，按账号范围、序号升序分页。游标代表已读取或已确认的日志位置，区别于单条文件的 `revision`。设备用已认证的 `user_devices` 身份绑定 `sync_devices`，仅在客户端已持久化应用结果或可恢复的待办后确认游标。服务端不接受超出已交付位置的确认，重复确认不回退。同账号不同设备各自确认。

**保留与重建。** 按原方案保留至少 90 天的变更日志，清理受保留窗口和有效设备确认共同约束，且只推进连续可裁剪前缀。重建时保留本地未提交变更，建立新快照并重新核对。[第 7 节](#7-变更日志与设备游标数据契约)细化可续传下界和游标失效条件。快照交付方式及上限、凭据格式在接口细化时定稿。

例如，设备从快照截止序号 20 开始，随后拉取 21、22 两个事件。它在持久化事件 21 的本地结果后崩溃，重试时仍可读取重复事件；按序号幂等处理后补齐 22。只有可恢复的本地结果才能推进确认。

## 3. 内容替换、历史配额与 GC

1. **准备。** 发起替换时绑定目标文件 ID、预期 `revision` 和新内容身份，按新内容的完整大小预占。复用 B4 尺寸分流、不可变暂存、校验及恢复能力。现有普通上传会发布一个新文件，替换路径需要明确的发布意图和独立契约。
2. **提交。** 新对象校验通过后，在账号事务内重新核对活动文件、完整祖先路径、版本、额度和对象状态。用 `file_versions` 保存旧版本及旧对象引用，保留旧内容的已用空间；更新当前引用和 `revision`，把新内容额度从预占转为已用。任务结果、幂等记录及变更事件与这些写入同时提交。重试返回同一结果。
3. **冲突。** 请求当场发现版本不符时返回 `409 REVISION_CONFLICT`，后台提交时发现的冲突通过任务结果公开同一业务码。客户端保留本地源，按第 9 节核对远端并处理冲突副本。
4. **到期。** 清理历史行时同事务释放该历史引用的计费，重复运行只释放一次。当前文件移入回收站仍按原规则计费；清理当前文件释放当前引用的额度，历史引用按自己的保留期结算。只要有有效当前引用、保留的历史行或保护任务，GC 就不能领取物理删除。

例如，当前 revision 4 的文件用量为 7 B，替换内容为 9 B。准备成功后已用 7 B、预占 9 B；提交后当前版本为 5，历史版本 4 仍计费，已用 16 B、预占 0 B；若其间没有其他操作，历史版本清理后已用降为 9 B。

## 4. 删除传播和冲突规则

- 单向备份不因本地删除而删除远端。双向同步须由用户单独开启，删除传播默认关闭；收到墓碑时仍要记录远端状态和同步位置。
- 显式开启删除传播时，只有源和目标仍与已确认基线相符，才按既有条件回收语义处理。删除与修改冲突时先保全修改内容。两端改动且摘要不同则保留两份，摘要相同则可合并为同一已同步状态。
- 游标过期、快照中断、同步根不可访问、扫描失败或文件授权丢失时，暂停相应删除动作。客户端在落盘替换前再核对本地内容，防止扫描之后的编辑被覆盖。文件监听和本地落盘行为由对应客户端阶段验收。

## 5. 隔离验收矩阵

| 场景 | 必须核对 |
| --- | --- |
| 迁移及兼容 | 空库、含 B4 合成条目及上传任务的版本 2 库均可升级并复跑；历史迁移摘要和已有内容、配额保持一致，缺序、dirty 和摘要错误明确拒绝；B3 与 B4 原入口回归通过 |
| 变更序号及事件覆盖 | 同账号并发提交按序可读；业务回滚没有残留事件或游标空档；发布、改名、移入移出同步范围、回收、恢复、批量清理及替换均产生可应用的事件；不同账号无法串读串写 |
| 快照、分页、设备确认及重启 | 快照期间并发写入可由后续增量补齐；分页读同一快照；重复和中断可恢复；越界、跨设备和已撤销设备的确认被拒；仅确认已持久化结果 |
| 游标过期、日志清理与恢复 | 90 天窗口及有效设备确认共同限制清理，过久离线须重建；旧快照和旧备份恢复前的游标失效；重建保留本地未提交变化且不据缺项执行批量删除 |
| 替换版本与冲突 | 两设备以相同旧 revision 提交不同内容，一个替换成功、另一个冲突；正常重试不重复替换或计费，冲突副本能读回且两端摘要与合成源各自一致；错误摘要、取消和故障路径不改变现有文件 |
| 历史留存与配额 | 旧版本按默认 30 天保留；新增内容全额预占并只结算一次；到期与重复清理只返还一次。历史行、活动文件、回收站和待发布任务仍保护各自引用的对象 |
| 删除传播与客户端安全 | 默认关闭时保留文件；显式开启后按已确认基线处理。覆盖删除与修改、文件移动、同步根失效和替换前本地再次编辑，核对内容仍能找回 |
| 备份恢复及回退 | 在全新隔离环境验证数据库、当前与历史对象版本、配额、日志位置和设备重建；用 B5 样本演练停写恢复及回退，核对不会因丢弃表或回放旧游标丢失 B5 新写入 |

验收使用独占 MySQL、版本化 MinIO 测试桶、回环服务及合成账号。沿用[隔离备份恢复手册](隔离备份恢复手册.md)的源端与目标端隔离规则，扩展历史对象、同步状态及回退样本。

## 6. 实施依赖和评审顺序

1. 评审本稿。细化 `change_events` 与 `sync_devices` 的字段、索引和有序迁移验证，复用现有 `change_seq`；为内容替换和历史引用保留独立迁移。
2. 先在账号事务内实现追加事件，再分批覆盖已有命名空间写入口。事件覆盖齐全后再交付快照、增量、设备确认及游标重建。完成确认及重建验收后接日志清理。
3. 先落实历史引用的配额与 GC 保护，再接通条件替换和历史到期清理。以两个隔离客户端验收冲突与重试，最后演练迁移、备份恢复与回退，对照第 5 节收尾。

接口细化交付需包含操作、必需字段、错误码、幂等、状态转移、事务边界和测试入口。游标、快照、替换任务在各自实现前写入 OpenAPI 契约。

## 7. 变更日志与设备游标数据契约

### 7.1 变更事件 change_events

| 字段 | 数据契约 |
| --- | --- |
| `user_id`、`sequence` | `BIGINT UNSIGNED NOT NULL`。主键 `(user_id, sequence)` 同时支持按账号有序拉取和裁剪，`user_id` 引用 `users(id)`。同账号第一个事件从 1 开始。 |
| `entry_id`、`revision` | `BIGINT UNSIGNED NOT NULL`，均为非零值。记录该次变更提交时的条目标识和版本。条目标识可在目录项墓碑清理后保留，无目录项外键。 |
| `event_type`、`payload` | 类型为非空的 `VARCHAR(32)`，使用 ASCII 区分大小写。载荷为 `JSON NOT NULL`，业务层校验为对象。按事件种类保存当次父目录、名称、内容标识或墓碑语义，由后续事件契约明确字段。 |
| `created_at` | `DATETIME(6) NOT NULL`，使用数据库 UTC 时间，供保留策略检查。 |

复用 `users.change_seq` 作为账号已提交的最大序号，同账号持有用户行锁后分配连续正整数。业务写入、序号推进和事件插入一起提交或回滚；同一事务产生多个事件时按确定次序分配。序号到达上限时拒绝继续提交。拉取按序号游标排他读取，事件排序与去重键以账号和序号为准。对外的标识、版本和序号沿用规范十进制字符串。

`DIRECTORY_CREATED` 表示通过 `POST /api/v1/directories` 首次成功创建普通目录。载荷示例为 `{"entry_id":"23","parent_id":"12","name":"资料","revision":"1"}`。ID、父项、展示名称和版本取自已写入并核对的目录，表列 `entry_id`、`revision` 与载荷对应。目录、幂等快照、事件和账号序号在同一事务提交。命中已有幂等结果时只交付原快照；事件追加失败随本次创建回滚。

`ENTRY_RENAMED` 表示通过 `PATCH /api/v1/entries/{id}` 首次提交了实际名称变更。文件和目录共用与 `DIRECTORY_CREATED` 相同的四字段载荷，记录同一条目、原父目录、已保存的新名称和递增后的版本。有效同名请求保留现有版本，按原规则保存幂等结果。它与同键重放、版本冲突均不产生事件。实际改名、幂等快照、事件及账号序号共同提交或回滚。

`ENTRY_MOVED` 表示通过 `POST /api/v1/entries/{id}/move` 首次提交了实际父目录变更。四字段载荷中的 `parent_id` 是新父目录，`entry_id` 和 `name` 保持原值，`revision` 为递增后的版本。移动目录时只为被移动条目追加事件，后代保留自己的直接父项和版本。有效同位置请求、幂等重放和版本冲突均不追加事件。移动、幂等快照、事件及账号序号共同提交或回滚。

`ENTRY_TRASHED` 表示通过 `POST /api/v1/entries/{id}/trash` 首次成功移入回收站。四字段载荷保留 `entry_id`、原 `parent_id`、原 `name` 和回收后的 `revision`。事件类型表示可恢复的软删除。回收目录时只记录回收根项，后代保留自身状态和版本，并通过祖先规则从活动目录隐藏。幂等重放、版本冲突及对已隐藏条目的新请求均不追加事件。回收、幂等快照、事件及账号序号共同提交或回滚。

`ENTRY_RESTORED` 表示通过 `POST /api/v1/trash/{id}/restore` 首次成功恢复条目。四字段载荷保留原 `entry_id`，使用服务端最终选定的 `parent_id`、`name` 及递增后的 `revision`。原位置不可用时记录回退后的父目录，活动同名时记录实际采用的后缀。目录恢复只为根项写事件，活动后代重新按祖先规则可见。重放与拒绝请求均不追加事件。恢复、幂等快照、事件及账号序号共同提交或回滚。

`FILE_PUBLISHED` 表示首次成功发布新文件。载荷保留 `entry_id`、`parent_id`、`name`、`revision` 四项，使用实际选定的位置、名称和初始版本。`size_bytes` 为已核对字节数的 JSON 整数，`sha256` 为已核对摘要的 64 字符小写十六进制字符串。

- `SINGLE` 和 `MULTIPART` 在后台读回校验通过后发布。Multipart 校验合并对象的指定版本。文件、任务、对象状态、配额、事件及账号序号共同提交或回滚。声明任务、合并待校验、校验失败和对已完成任务再次确认均不追加事件。
- `POST /api/v1/files/reuse` 使用同账号已有且可见的已校验对象。新文件条目、配额、首次幂等结果、事件及账号序号共同提交或回滚。同键重放只交付原快照，内容未命中或请求冲突不追加事件。

`FILE_CONTENT_REPLACED` 表示同一文件发布了新的内容版本。载荷沿用 `FILE_PUBLISHED` 的六个字段，`entry_id`、`parent_id` 和 `name` 取自替换完成时的文件快照，`revision` 是递增后的版本，`size_bytes` 和 `sha256` 对应实际校验的新内容。后台替换成功路径在同一发布事务追加事件。同步设备可以用相同 `entry_id` 更新现有条目的内容版本。

`ENTRY_PURGE_STARTED` 表示回收站根项从 `TRASHED` 进入 `PURGING`。载荷记录该根项的 `entry_id`、`parent_id`、`name` 及新 `revision`，子孙条目由既有祖先规则管理。该事件表示根项已进入不可恢复的清理流程，分批完成与引用结算由后续事件覆盖。状态、事件和账号序号共同提交或回滚。

- `DELETE /api/v1/trash/{id}` 首次受理时，还在同一事务保存 `202` 快照。预检拒绝、版本冲突及幂等重放均不追加事件。
- 后台到期标记成功时使用同一载荷。未超过 30 天保留期、扫描后已失效、被回收祖先覆盖及本轮上限之外的候选当轮不追加事件。

`ENTRY_PURGED` 表示逻辑清理已将单个条目推进到 `PURGED`。载荷保留 `entry_id`、`parent_id`、`name` 与实际落库的 `revision`，作为该条目的墓碑。每个成功结算的文件、子目录和最后处理的清理根项各有一条事件。同一批按现有叶子处理顺序追加，事件及账号序号与状态、配额、对象引用、回收计时和偏好一起提交或回滚。版本已达上限时沿用原版本，客户端仍按账号序号识别完成事件。过期候选和已完成条目的重复处理不会再次结算，也不追加事件。

### 7.2 同步设备 sync_devices

| 字段 | 数据契约 |
| --- | --- |
| `device_id`、`user_id` | `BIGINT UNSIGNED NOT NULL`，主键为 `device_id`。索引 `(user_id, device_id)` 对应至 `user_devices(user_id, id)` 的复合外键。调用方以认证身份的账号和设备取数。 |
| `ack_sequence` | `BIGINT UNSIGNED NOT NULL DEFAULT 0`。当前基线代次内，记录本设备已持久化处理或登记可恢复待办的最大连续位置。合法重复和较旧确认保持原值；不同设备独立推进。 |
| `status`、`cursor_generation` | `status` 为区分大小写的 `VARCHAR(16) NOT NULL`，仅 `ACTIVE`、`RESET_REQUIRED`，默认 `RESET_REQUIRED`。`cursor_generation BINARY(16) NOT NULL` 保存服务端生成的随机代次，绑定快照及拉取、确认凭据。 |
| `last_seen_at`、`created_at`、`updated_at` | `DATETIME(6) NOT NULL`，记录 UTC 的最近成功同步活动、创建和更新时间。保留期使用同步活动时间，认证活动仍由 `user_devices` 维护。 |

设备首次启动同步时创建同步行。重建基线时，在所属用户事务中置 `RESET_REQUIRED`、将确认位置归零并更换代次。客户端持久化同一代次的快照后，服务端复核快照截止序号仍可续读，再记录该序号并置 `ACTIVE`。开始另一份基线会使前一份快照凭据失效。增量确认须提供能证明已交付位置的服务端凭据，服务端在账号事务内复查账号、设备、代次、状态和范围后推进位置。设备撤销时同步失效也须在账号锁内处理，后续重新登录沿用原设备 ID，重新建立同步基线。

### 7.3 可续读范围和失效条件

在同一只读一致性视图里取账号的当前最大序号 `H` 和仍保留的最早事件序号 `first`。可接受的最小游标为 `first - 1`；日志为空时等于 `H`。这一推导依赖保留区间连续，清理方只允许从头裁剪，拉取按 `sequence > cursor` 读取并核对连续性。

| 观察结果 | 处理 |
| --- | --- |
| 账号和设备合法、代次一致，位置在最小可读游标和 `H` 之间（含边界） | 继续拉取。位置恰为 `H` 时正常返回空页；确认还须处于该设备的已交付范围。 |
| 位置低于最小可读游标、同步状态为 `RESET_REQUIRED` 或凭据属于同设备的旧代次 | 返回 `CURSOR_EXPIRED`，客户端保留本地未提交内容并重建快照。 |
| 位置高于 `H`、确认超过已交付位置、凭据格式或签名无效、账号或设备绑定不符 | 正常拒绝，保留设备已确认位置；授权失败沿用既有身份检查。 |

例如，`H=22`，现存日志 18～22，最小可读游标是 17。游标 17 可取回 18～22，16 须重建，22 正常返回空页。如果 18～22 已全部按策略裁剪，最小游标变为 22。

裁剪在所属账号锁内复核日志保留时间和有效设备的最小确认位置，从开头删除满足两项门槛的连续前缀。后台先按[第 14 节](#14-离线设备重建)处理离线设备，再根据已提交的设备状态判断日志可清理范围。在旧备份恢复后的同步入口开放前，先重置所有恢复出来的同步设备并刷新代次，使旧凭据在相同序号再次出现时仍失效。

## 8. 历史版本数据与迁移契约

以 [数据库方案第 6.2 节](数据库设计方案书.md#62-file_versions) 为字段基线。每行表示一次成功内容替换保留下来的旧内容引用，条目 ID 保持稳定，版本取替换前的 `file_entries.revision`。改名、移动和回收沿各自的命名空间规则处理，历史行专用于保留被替换的内容。

### 8.1 字段与约束

| 字段 | 数据契约 |
| --- | --- |
| `id` | `BIGINT UNSIGNED NOT NULL AUTO_INCREMENT`，主键。同一到期时间用它确定处理顺序。 |
| `user_id`、`entry_id`、`object_id` | `BIGINT UNSIGNED NOT NULL`。使用 `(user_id, entry_id) → file_entries(user_id, id)` 和 `(user_id, object_id) → stored_objects(owner_user_id, id)` 两个复合外键，以已有父表唯一索引验证同账号归属。 |
| `revision` | `BIGINT UNSIGNED NOT NULL`，`CHECK (revision > 0)`。`UNIQUE (entry_id, revision)` 防止同一条目版本被重复保留；不同条目可各自保存相同版本号。 |
| `file_size` | `BIGINT UNSIGNED NOT NULL`，允许零字节。锁内核对其与旧条目逻辑大小和已校验对象大小一致，供配额结算。 |
| `created_at`、`retained_until` | `DATETIME(6) NOT NULL`，`CHECK (retained_until > created_at)`。写入方取同一次数据库 UTC 时间作为开始保留时刻和截止时间的计算基准。默认保留 30 天，配置变更只影响此后新建的历史行。 |

表沿用 InnoDB 与首期字符集。外键限制父记录的物理删除，避免级联清掉计费记录。保留中或已到期但尚未结算的行允许指向 `PURGED` 文件条目，原条目墓碑的物理清理须等其历史引用结算完毕。业务写入在账号事务内验证目标为可替换的活动文件、完整祖先路径可用、旧对象为 `READY` 且已校验，并比较版本、大小和内容引用。

| 索引前缀 | 用途 |
| --- | --- |
| `(user_id, entry_id)` | 支撑目录项复合外键并按所属条目查找保留行。 |
| `(user_id, object_id)` | 支撑对象复合外键，在锁内按归属判断某对象是否还有历史引用。 |
| `(retained_until, id)` | 以数据库 UTC 时间扫描到期记录，以 `id` 打破同一截止时间的并列。 |

历史行存逻辑大小和对象 ID，内容摘要、桶、键与物理版本沿用已校验的 `stored_objects` 记录。同一个对象可同时服务多个当前或历史引用，每个逻辑引用各自计费。

### 8.2 事务、配额与引用保护

1. **替换提交。** 在所属账号行锁下复核目标、旧版本和已校验的对象。将旧引用写入 `file_versions`，再更新当前文件并递增版本。旧字节已经在已用配额中，转为历史引用时保留原用量；新字节从该任务的全额预占转为已用。历史行、当前引用、任务和幂等结果、配额、变更事件一起提交。冲突、取消、失败和同键重放都不会额外产生一条历史引用。
2. **GC 保护。** [回收计时、候选领取和暂存孤立的共用复核](../internal/server/repository/stored_object_references.go)在所属账号和对象锁内，用 `(user_id, object_id)` 当前读检查历史行。只要历史行仍存在，即使 `retained_until` 已到，也会阻止启动回收计时或领取物理删除。外键约束 SQL 记录，共用复核保护存储中的实际内容。替换把当前引用转为历史引用时，应维持有效引用的两个回收计时字段为空。持有历史引用保护的对象须能读回原版本。
3. **到期结算。** 扫描 `retained_until <= UTC_TIMESTAMP(6)` 的候选后，先锁账号、按归属锁对象，再锁历史行并复核归属、版本、截止时间和计费大小。删除该行并扣减相应已用空间，两项一起提交。旧候选、重复结算和并发中已删除的行不再扣费，预占保持原值。若仍有其他当前文件、历史行或非终态任务保护对象，继续保留内容；最后一个引用释放后，在同一事务开始现有七天回收宽限期。状态、大小、配额或计时异常时回滚，供下一轮复查。
4. **配额与恢复。** 汇总时，`used_storage` 等于未进入 `PURGED` 的当前文件大小，加上仍存在的历史行大小。`reserved_storage` 仍按任务预占汇总。备份须覆盖历史引用及其独占对象，按对象 ID 去重保存正文；恢复核对引用、大小、原对象版本和配额，确认回收保护生效后才开放后台写入。

例如，当前文件使用 7 B，替换为 9 B 后会有一条计费 7 B 的历史行，已用为 16 B。期限到达时若清理 worker 尚未提交，已用仍是 16 B，旧对象仍受保护。历史事务提交后已用降至 9 B；若旧对象没有其他引用，才开始七天宽限期。

后续运行时验收覆盖截止前 1 微秒、恰好到期和已到期但尚未结算三种状态。用同一对象的多个逻辑引用验证每行单独计费和最后引用规则，并让到期结算与 GC 领取并发，核对只有取得账号锁且仍符合条件的事务能推进。

单条历史写入使用 `SaveCurrentFileVersion`。调用方在所属账号事务中给出文件 ID、预期版本和保留天数，再在同一事务完成当前引用更新与配额结算。历史写入锁读当前文件、活动父链与旧对象，并拒绝已有回收计时的旧对象。重复 `(entry_id, revision)` 返回领域冲突，保留原行及截止时间。统一重放由外层替换任务与幂等契约处理。 [仓储实现](../internal/server/repository/save_current_file_version.go)

### 8.3 迁移范围与隔离验收

## 9. 条件内容替换与上传任务

### 9.1 准备请求与传输

服务启动时按 [OpenAPI](../api/openapi.yaml) 注册 `POST /api/v1/entries/{id}/content-replacement`。路径 `id` 标识既有文件，正文提交 `expected_revision`、`size_bytes` 和整文件 `sha256`。版本取自客户端已读取的文件条目，使用非零 uint64 十进制字符串。大小为非负整数，两种上传模式都要求 64 字符十六进制摘要，大小写规范化后等价。目标归属、来源设备取自已认证身份。普通上传创建新文件，继续使用 `POST /api/v1/uploads`。

1. 认证后校验路径、`Idempotency-Key` 及正文。在已认证账号事务中按账号、替换创建操作和幂等键查找回执。摘要绑定目标 ID、预期版本、字节数和规范化摘要。有效同键同参数重放原 `201` 快照并交付本次请求 ID。同键异参或已过期回执沿用 `IDEMPOTENCY_CONFLICT`、`IDEMPOTENCY_EXPIRED`。
2. 首次准备锁读同账号文件和完整活动祖先链。目标缺失、跨账号或不可见时返回 `404 ENTRY_NOT_FOUND`。可见目录返回字段 `id` 的 `400 INVALID_ARGUMENT`，可见文件版本失配返回 `409 REVISION_CONFLICT` 和 `details.current_revision`。版本达到上限且匹配时沿用既有 `500 INTERNAL_ERROR`，保护版本不回绕。任何拒绝均无新增预占或任务。
3. 校验配置及存储大小上限和剩余配额，超限返回 `413 FILE_TOO_LARGE`，额度不足返回 `507 QUOTA_EXCEEDED`。按新内容全额预占，原用量保持原值。预占、暂存对象、带替换绑定的任务和成功回执一起提交。成功回执保留八天，初始任务期限为 24 小时。
4. 复用现有尺寸分流。0 到 16 MiB（含）返回 `SINGLE/UPLOADING` 和内容路径，超过 16 MiB 返回 `MULTIPART/CREATING` 和固定分片计划。客户端保存任务 ID，沿用该任务的内容、分片、完成、查询和取消操作。两条路径都要按现有不可变对象定位规则读回并核对整文件大小与 SHA-256，有存储版本时绑定该版本。客户端申请完成或收到 `202` 只表示当前上传阶段，发布结果以任务终态为准。

### 9.2 任务绑定、发布与冲突

替换任务在 `upload_tasks` 持久保存 `replacement_entry_id` 和 `replacement_expected_revision`。两者同为空表示新建文件，两者都有值表示替换，后者必须是正整数。目标通过 `(user_id, replacement_entry_id)` 复合外键约束到同账号文件条目，状态和路径仍由事务复核。已有任务升级后两者均为空。现有父目录和请求名保留准备时的快照，供通用传输数据使用。`result_entry_id` 仍是发布结果，只在发布成功后填入，不能用来判断任务意图。

替换任务的通用公开响应额外携带 `replacement`，含 `entry_id`、`expected_revision`、`published_revision`、`conflicting_revision`。创建快照中两个结果版本为 `null`。`COMPLETED` 时 `result_entry_id` 等于目标，`resolved_name` 为保留的文件名，`published_revision` 等于预期版本加一。发布时发现版本冲突则保存 `FAILED / REVISION_CONFLICT`，`conflicting_revision` 取冲突判定时锁读到的可见文件版本。其他失败、取消和过期均无结果版本。任务持久保存结果版本，后续查询或重复完成不会把它替换成文件此刻的版本。普通任务继续交付原有字段。

[版本 5 迁移](../migrations/000005_upload_replacement.up.sql) 为结果分别增加 `replacement_published_revision` 和 `replacement_conflicting_revision`。四个新字段都是可空的无符号 64 位整数，普通任务四列为空。数据库校验绑定、同账号归属及结果版本与任务状态的一致性。外键限制仍被任务引用的目标条目物理删除。文件类型、可见路径和版本在事务内复核。复验见 [第 812 步学习记录](开发学习记录.md#第-812-步新增上传替换任务绑定与结果版本迁移)。

1. **复核发布资格。** 后台事务锁住所属账号，重新核对任务状态、租约、期限和已校验对象身份，再锁读目标文件及完整可见祖先链，比对原预期版本和任务预占。只以任务中的绑定定位目标。目标不可见或已不可用时沿用 `FAILED / TARGET_UNAVAILABLE`。
2. **提交替换。** 复用 `SaveCurrentFileVersion` 保存旧版本及旧对象引用。保持原文件 ID、父目录、名称和创建时间，更新当前对象、内容大小、内容 MIME 和修改时间，递增版本一次。旧用量转由历史行承载，新用量从本任务预占转为已用，分别按逻辑大小计费。对象就绪状态和回收保护、当前文件、历史行、配额、`COMPLETED` 快照及账号事件在同一事务中确认。成功追加一条 `FILE_CONTENT_REPLACED`，载荷沿用 `FILE_PUBLISHED` 的六个字段，使用现有条目和实际发布的新版本、字节数及小写摘要。准备回执仍保留首次 `201` 的任务快照。
3. **提交失败或重试。** 已确认的版本冲突与 `TARGET_UNAVAILABLE` 终态同事务释放全额预占，未被引用的暂存对象走现有孤立和宽限期回收流程。原当前文件、旧历史、已用配额和变更日志保持原样。取消与过期走既有终结流程，失去租约的执行者不得提交发布。数据库等暂时故障按既有重试规则处理。已完成任务重读已提交的结果，已失败任务通过任务查询交付原因。
4. **保全冲突内容。** 客户端在确认替换或冲突副本已发布前保留本地源。冲突后重新读取远端，摘要已经相同可合并同步状态；内容不同则用带设备标识和唯一后缀的新名称提交普通上传。仅当内容独立满足既有同账号、可见且已校验条件时，才用 `POST /api/v1/files/reuse`。失败任务的暂存对象不作为可复用来源。客户端不得用新版本号重放原替换来覆盖另一设备的修改。

只有发布器能按任务绑定分流并保证上述提交与失败收尾时，才启用替换创建入口。

后台已可在选定发布对象前确认版本冲突或替换目标不可用，再以同一事务保存失败结果和预占释放。版本冲突保留冲突版本，目标不可用记录 `FAILED / TARGET_UNAVAILABLE`，两个结果版本均为空。无引用的暂存对象沿用七天回收宽限期。已有任务查询、完成和取消成功响应共用公开映射，普通任务省略 `replacement`。

### 9.3 隔离验收

| 场景 | 可核对结果 |
| --- | --- |
| 准备和兼容 | 用 0 B、正好 16 MiB 及多 1 B 的合成样本核对模式和全额预占。缺失摘要、过期版本、不可见目标、跨账号及额度不足均无新增任务或预占。两种模式同键重试、不同版本同键冲突，既有普通任务仍按原入口和格式工作。 |
| 发布和恢复 | 核对文件 ID、父目录和名称不变，当前对象及版本更新，新旧两个摘要均可独立读回。旧版本按默认 30 天留存，新大小全额且只结算一次。重复完成仍交付原发布版本。在事务写入中途注入错误，各项一起回滚。 |
| 并发和失败 | 两设备先用同一版本创建不同内容的任务，再并发完成。只有一个可提交，另一任务保存冲突版本、释放预占、无新增历史或事件，之后可发布并读回独立副本。用错误摘要、目标变为不可见、取消与过期夹具核对当前内容和已用空间不受影响。 |

## 10. 一致性快照的创建与分页

本节定义首次同步及重建基线的快照契约。创建和续页已在服务启动时注册，接口见 [OpenAPI](../api/openapi.yaml)。首版以当前账号整棵活动目录树作为基线，与账号级变更序列对应。客户端自行选择本地同步范围。

### 10.1 创建和固定内容

1. Bearer 授权后，以认证的账号、设备及会话处理 `POST /api/v1/sync/snapshots`。请求含 `Idempotency-Key` 和 JSON 对象，`page_size` 可省略，默认 50，范围 1～100，创建后固定。成功返回 `201` 和第一页。
2. 按 [现有只读快照事务](../internal/server/repository/file_entry_snapshot.go)的五秒上限，在同一个 MySQL 可重复读视图取得真实根目录、`users.change_seq` 和所有可达的活动文件及目录。活动祖先链沿用现有可见性与深度约束。根目录通过 `root_entry_id` 返回。条目按 `entry_id` 数值升序，客户端以 `parent_id` 建树，允许父项和子项落在不同页。
3. 每项包含条目 ID、父目录 ID、名称、类型、版本、字节数和 SHA-256。ID、版本和截止序号使用完整 uint64 十进制字符串，只有截止序号允许 `0`。文件使用同一读取视图中按归属找到的 `READY` 对象，核对大小及已校验摘要。目录固定为 0 B 和 `sha256: null`。可见文件内容记录异常时整份创建失败。快照提供元数据，后续下载仍通过正式授权接口并提交条目版本。
4. 首版采用单进程不可变缓存，单份最多 10,000 个条目和 8 MiB UTF-8 序列化条目数据。进程内最多 2 个并发构建、32 份构建中或已就绪的快照、64 MiB 的缓存及构建数据预留预算。任一单份上限超出返回 `422 SNAPSHOT_TOO_LARGE`，超过进程准入预算返回 `503 SNAPSHOT_BUSY`。完整快照入缓存后从该时刻起有效 10 分钟，读页和重放均不延长。到期或代次失效的缓存按生命周期清理。服务实例重启后，仍需读取页的客户端重新创建快照。
5. 先完整读出、关闭只读事务并为拟用新代次准备缓存，再在账号锁内复验会话、设备、幂等键及截止序号仍可续读。写入或更新当前设备的 `sync_devices` 为 `RESET_REQUIRED`、`ack_sequence=0` 并保存该新代次和创建回执，一起提交。缓存只有在持久化代次匹配时才可交付。大小超限、构建失败、重验失败或事务回滚均保留原设备状态，释放本次构建预算。不同键创建成功后，旧代次的分页及确认凭据失效。已提交后若进程在返回响应前退出，同键重读首页按快照失效处理。
6. 使用既有按账号和操作隔离的幂等表，操作名为 `v1.sync.snapshots.create`，摘要绑定设备 ID 和规范化后的页大小。在首次读取和最终提交前检查同键回执，并发同键只提交一份代次。回执保留 8 天，仅保存设备及快照定位元数据；原第一页从固定缓存重读。同键同参数且快照有效返回同一 `201` 数据和本次请求 ID，快照失效返回 `410 CURSOR_EXPIRED`。同键不同设备或参数、幂等记录到期分别按既有 `409 IDEMPOTENCY_CONFLICT`、`409 IDEMPOTENCY_EXPIRED` 处理。重建使用新键。

### 10.2 固定分页与基线交接

- `GET /api/v1/sync/snapshots/{snapshot_id}?cursor=…` 读取服务端交付的下一页。快照 ID 为小写 UUID v4。分页凭据采用专用用途的版本化签名文本，绑定账号、设备、快照 ID、代次、固定页大小、下一位置及过期时间。路径和绑定须同时匹配。缺少、空白、重复、篡改或错用的分页凭据返回 `400 INVALID_CURSOR`，同一设备的合法凭据因过期、代次变化或缓存丢失而失效时统一返回 `410 CURSOR_EXPIRED`。每次读取重新走现有授权。
- 各页用同一份缓存交付 `snapshot_id`、`root_entry_id`、`high_water_sequence`、`expires_at` 和 `items`，响应用 `Cache-Control: no-store`。同一有效凭据可重读同页。非末页给出 `next_cursor` 且 `baseline_token` 为 `null`。末页及空目录树给出末页确认凭据 `baseline_token`，`next_cursor` 为 `null`。两类签名用途独立。生成或读取页只交付数据与凭据。
- 版本 1 续页凭据的账号和设备标识是标准十进制字符串，`generation` 将完整的 16 字节 `cursor_generation` 编码为 32 个小写十六进制字符。校验后还原完整字节，与设备当前已持久化代次比较。
- 版本 1 末页确认凭据使用 `cloudnest/sync-snapshot-baseline/v1` 签名用途，绑定账号、设备、快照 ID、完整代次、截止序号和原到期时刻。截止序号以十进制字符串编码，允许 `0`，到期时间沿用原快照的 UTC 时刻。
- 客户端按同一快照 ID 暂存各页，持久化整份基线或可恢复待办后才使用末页凭据确认。确认按[第 11 节](#11-设备基线确认)执行。首次增量按[第 12 节](#12-增量变更拉取)从本地已持久化的截止序号之后拉取。
- 收到 `CURSOR_EXPIRED` 时保留本地未提交内容，用新键创建快照并替换整份远端基线。不得从新快照继续拼接旧页，也不得因快照缺项推断应删除本地文件。若后续增量中恢复事件揭示了基线中缺失的子树，暂停该处删除操作并重新取得完整基线，避免把仅含根项的恢复事件当成完整子树。

### 10.3 隔离验收

| 场景 | 预期 |
| --- | --- |
| 同一视图与续页 | 在读取序号后提交并发重命名、移动、内容替换或回收，各页仍返回同一个截止序号和原视图内容。已提交变更位于截止序号之后。反复读取同一页不漏项，最后页及空页仅交付末页凭据。 |
| 身份与重试 | 同账号的另一设备、跨账号、已撤销会话、路径不符、篡改或凭据用途错用均拒绝。同键并发和丢失创建响应后重试均返回同一份快照，重建提交后旧代次失效。 |
| 上限与生命周期 | 10,000 条、8 MiB、固定页大小和过期时刻的边界按约定处理，超限及事务故障不改变设备状态。仍需读取页时，缓存缺失或服务重启后走完整重建，保持本地未提交数据。 |

## 11. 设备基线确认

`POST /api/v1/sync/snapshots/{snapshot_id}/confirm` 在服务启动时注册。使用现有 Bearer 授权，账号、设备和会话取自认证结果。路径沿用小写 UUID v4，正文为未压缩的 UTF-8 `application/json` 对象，仅接受一个 `baseline_token` 字符串。原样提交同一快照的末页凭据，长度上限 1024 字符。拒绝空值、空白、重复字段及未知字段。重复确认依靠签名凭据和已提交的设备状态，无需创建快照使用的幂等键。

### 11.1 确认顺序

1. 解析路径和正文，验证 `cloudnest/sync-snapshot-baseline/v1` 签名、规范格式及账号、设备、快照 ID 的绑定。可信凭据只在 `now < expires_at` 时有效。凭据携带完整的 16 字节代次、截止序号和快照原到期时刻。客户端无需另传这些字段。翻页使用的 `next_cursor` 在本端点无效。
2. 进入 `WithUserTransaction`，在所属账号锁内重新确认账号、设备及会话可用。检查该设备的同步记录和完整代次，在锁内复核凭据到期时间及 §7.3 的日志范围。设 `H` 为当前账号序号、`first` 为仍保留的首条日志序号。截止序号必须在 `[first - 1, H]`，日志为空时仅接受 `H`。快照页缓存仅用于创建和续页。已保存末页凭据的客户端可在服务重启后确认，仍须通过签名和账号事务内的全部检查。
3. 若同代设备为 `RESET_REQUIRED` 且确认位置为 0，将其置为 `ACTIVE`，同时把 `ack_sequence` 设为凭据的截止序号并更新本次同步活动时间，允许序号为 0。若设备已是 `ACTIVE` 且当前位置不小于凭据截止序号，有效重试直接读取已有位置，无需更新设备行。重试同样复核凭据期限与截止序号，代次变化、到期或日志已无法从该基线续读时返回 410。未知状态、待重建状态的非零确认位置或活动状态位置与凭据及账号序号矛盾时返回 500。
4. 事务成功提交后返回 `200`，`data.status` 固定为 `ACTIVE`，`data.ack_sequence` 是本次事务确认的设备位置，使用允许 `0` 的完整 uint64 十进制字符串。外层 `request_id` 对应本次请求，确认响应禁止缓存且不回显凭据。重试可能读到后续增量已推进的位置，客户端仍以本地已持久化的位置请求增量，避免跳过尚未应用的事件。若确认结果因连接中断而未知，在原凭据有效期内可重试。

### 11.2 错误与隔离验收

| 场景 | 预期 |
| --- | --- |
| 首次确认和并发重试 | 使用空账号的零序号和含事件的非零序号验收。两个同一凭据的并发请求最多执行一次状态转换，均可返回已提交位置。已有增量确认后重试不把位置向后改。 |
| 绑定或格式错误 | 非法路径或 JSON 结构返回 `400 INVALID_ARGUMENT`。缺少、空白、超长、篡改、错用用途或绑定不符的凭据返回 `400 INVALID_CURSOR`，字段为 `baseline_token`。拒绝请求保持已确认位置。 |
| 授权变化 | 缺少有效授权、会话到期或撤销、设备撤销沿用现有 401，账号禁用沿用 403。用请求进入账号事务前撤销会话的夹具验证锁内复核。 |
| 可信凭据失效 | 同设备合法凭据在恰好到期、等锁期间到期、同步行缺失、代次改变或截止序号低于最小可读位置时返回 `410 CURSOR_EXPIRED`。客户端保留本地未提交内容，使用新幂等键创建完整快照。 |
| 日志边界和进程重启 | `H=22`、最早事件 18 时，首次确认接受 17 和 22，16 返回 410。日志为空只接受 22。服务重启且持久化代次与签名密钥保持有效时，用已保存且仍可续读的末页凭据确认成功。 |
| 事务故障 | 截止序号大于 `H`、日志边界异常、数据库故障或无法确认提交结果时返回通用 `500 INTERNAL_ERROR`。已回滚的事务保留设备原状态与位置，提交结果未知时以同一合法凭据重试并观察持久状态。统一 JSON 绑定的 413、415 沿用既有契约。 |

## 12. 增量变更拉取

`POST /api/v1/sync/changes/pull` 在服务启动时注册，操作只读。使用 Bearer 认证，账号、设备和会话取自认证结果。凭据随未压缩的 UTF-8 `application/json` 对象提交。仅允许 `baseline_token` 或 `cursor` 二选一，以及可选的整数 `page_size`。默认 50，上限 100，最小为 1。正文沿用 1 MiB 上限和精确字段名，拒绝重复、额外字段和显式空值。

### 12.1 首次拉取与续读

1. **首次拉取。** 客户端持久化完整快照并确认后，在末页凭据的原有效期内提交 `baseline_token`。复用末页验签规则，校验凭据用途、账号、设备及原到期时间，快照 ID 来自受签名保护的载荷。当前设备须为 `ACTIVE` 且完整代次一致，持久确认位置须至少达到凭据的截止序号。即使设备已确认到更高位置，本次拉取仍从该凭据记录的截止序号之后开始。首次收到响应后，把增量游标与本地已处理事件或可恢复待办一起持久化。若客户端尚无增量游标且末页凭据已过期，按 410 重建基线。
2. **后续拉取。** 原样提交已持久化的 `cursor`。增量游标使用独立签名用途 `cloudnest/sync-change-pull/v1`，绑定账号、设备、完整 16 字节代次和最后已交付的序号。文本为两个以句点分隔的无填充 Base64URL 段，最多 1024 字符。续读游标可跨同设备的有效会话和服务重启使用，在签名密钥、当前代次和日志保留范围继续有效时可重复使用。凭据不设独立时间期限，离线重建和日志裁剪仍会使游标失效。页大小可逐次调整。
3. **本地提交。** 收到响应后先在本地持久化按序应用的结果或可恢复待办，再保存返回游标。连接中断或处理未持久化时，使用上次已保存的凭据重拉。按账号与序号去重。拉取本身不推进服务器确认位置，也不刷新同步活动时间。持久化后按[第 13 节](#13-设备增量确认)提交增量确认。

第 1 版增量游标载荷依次使用 `version`、`user_id`、`device_id`、`generation` 和 `sequence`。版本为整数 `1`，账号和设备为非零 uint64 十进制字符串，序号为允许 `0` 的 uint64 十进制字符串，代次为完整 16 字节对应的 32 个小写十六进制字符。

### 12.2 每页读取与响应

1. 在一个最多五秒的只读一致性事务中，按认证身份核对设备及同步状态，读出 `users.change_seq` 作为本页上界 `H`，以及最早保留的序号 `first`。按照 §7.3 接受 `[first - 1, H]`，日志为空时仅接受 `H`。设备状态、当前代次、边界及事件来自同一视图。
2. 只读本账号的 `sequence > position AND sequence <= H`，按序号升序返回最多 `page_size` 条。应读条数为 `min(page_size, H - position)`。逐项核对序号连续、外层标识与载荷一致及 §7.1 的载荷格式。缺行、内部断档、无效事件或不可能的设备确认位置使整页失败，响应无事件和新游标。分页上界只用于本页，后续请求可读取此后提交的变更。同一凭据重拉从同一位置开始，期间保留范围可能变化。
3. `200` 响应包含 `data.events`、`data.high_water_sequence`、`data.next_cursor`、`data.has_more` 和外层 `request_id`，设置 `Cache-Control: no-store`。每条事件公开 `sequence`、`entry_id`、`revision`、`event_type` 和 `payload`。序号、标识和版本为规范 uint64 十进制字符串，事件序号、标识和版本须非零。本页上界允许 `0`。`payload` 沿用 §7.1 的四字段或六字段对象，随发布或内容替换交付已核对的大小和摘要。其他事件交付提交时的元数据，包括墓碑。下载仍走正式授权入口。
4. `next_cursor` 始终签在本页最后实际交付的位置。若 `position == H`，事件为 `[]`，游标签在原位置，`has_more=false`，可用作下一次轮询的起点。非空页的最后位置低于本页 `H` 时 `has_more=true`，否则为 `false`。客户端仅在本地持久化对应事件后推进本地游标。

例如，保留日志 18～22，从位置 17 拉取两条，返回 18、19 及位置 19 的游标。下一页从 20 开始。若此时新提交了 23，下一页的新上界可以是 23。当本地处理到该页所见的最后序号后，可用返回游标轮询后续提交。

### 12.3 失败与隔离验收

| 场景 | 预期 |
| --- | --- |
| 首次与续读 | 零序号基线可收到第一条事件。已确认的末页凭据在原期限内可取得第一页。若设备已确认到更高位置，首次拉取仍从签名的快照截止序号开始。空页也能取得可持久化游标。 |
| 顺序与并发 | 以小页跨越边界，并发提交只在之后的读取视图出现。重拉可重复交付相同序号。页内连续无缺项，`has_more` 与本页上界一致，确认位置和时间字段保持原样。 |
| 请求或绑定错误 | 正文结构和页大小错误返回 `400 INVALID_ARGUMENT`。错误签名、用途、身份绑定、游标位置高于 `H` 或无效的凭据文本返回 `400 INVALID_CURSOR`，定位 `cursor` 或 `baseline_token`。共享正文绑定的 413、415 保持一致。 |
| 身份和失效 | 授权失败沿用已有 401 和 403。末页凭据过期、同步行缺失、状态待重建、旧代次或位置低于可续读下界时返回 `410 CURSOR_EXPIRED`。客户端保留本地未提交内容并取得新快照。 |
| 日志异常 | 预期应交付的连续页缺行、异常载荷、矛盾状态或数据库故障返回通用 `500 INTERNAL_ERROR`，无部分结果。客户端保留已持久化位置并暂停受影响的删除，等待故障排查。 |

## 13. 设备增量确认

`POST /api/v1/sync/changes/confirm` 已接入服务启动，使用现有 Bearer 认证。客户端持久化已交付事件的处理结果或可恢复待办后，原样提交拉取响应的 `next_cursor`。请求正文为未压缩的 UTF-8 `application/json` 对象，上限 1 MiB，只含一个 `cursor` 字符串，遵循第 12 节的双段 Base64URL 格式和 1024 字符上限。确认位置直接取自签名中的 `sequence`。账号、设备和会话从认证得到，请求不接受单独的序号、身份字段或末页凭据。重复确认通过设备状态和游标位置判断，无需幂等键。

### 13.1 账号事务和状态变更

1. 先认证，再解析正文并使用现有增量游标校验器验证签名、用途、版本、账号和设备绑定。有效凭据可随同设备的新会话使用。异账号、异设备和不同用途的凭据在事务前被拒绝。
2. 进入最多五秒的 `WithUserTransaction`，按既有锁序复核账号、设备、会话并锁读当前同步行。同步行缺失、设备处于 `RESET_REQUIRED` 或完整代次不匹配时返回 `CURSOR_EXPIRED`。未知状态、无效代次或待确认行带非零确认位置属于内部数据错误。
3. 在账号锁内按 §7.3 读取当前上界 `H` 和最小可续读位置 `M`。日志为空时只接受位置 `H`。日志区间矛盾或设备已确认位置高于 `H` 返回内部错误。请求位置高于 `H` 返回 `INVALID_CURSOR`，低于 `M` 返回 `CURSOR_EXPIRED`。重复和较旧的确认也须满足这些检查。
4. 比较签名位置 `S` 和设备已确认位置 `A`。若 `S > A`，推进 `ack_sequence` 到 `S`。若 `S == A`，只记录本次同步活动。若 `S < A`，保持记录原样。推进与等值确认均在同一事务用数据库 UTC 微秒时间更新 `last_seen_at` 和 `updated_at`，条件限制为当前账号、设备、`ACTIVE`、完整代次和原确认位置。等值确认在同一微秒无值变化时仍成功。该操作保持代次和状态，不写入新的变更事件。
5. 事务成功提交后返回 `200`，`data.status` 为 `ACTIVE`，`data.ack_sequence` 是事务确认的当前位置，编码为允许 `0` 的规范 uint64 十进制字符串。外层携带 `request_id`，禁止缓存并省略凭据。请求较旧时返回存储中已有的更高位置，客户端仍用自己已持久化的游标拉取。若响应丢失，可重试仍有效的同一游标。

例如，设备已确认到 `17`，读取并持久化 `18、19` 后用签在 `19` 的游标确认。首次确认推进到 `19`，重复确认记录活动时间，两者均返回 `19`。若随后已确认到 `22`，再次提交仍在保留范围内的 `19` 会返回 `22`，设备行不再写入。空页的游标也可以确认，处于当前确认位置时用于报告同步活动。

### 13.2 错误与隔离验收

| 场景 | 预期 |
| --- | --- |
| 确认推进与零位置 | 只用真实拉取生成的游标确认。合法非空页可推进，空页可确认现有位置，包括零序号。查询确认位置及 UTC 活动时间，验证无新事件且账号上界原样。 |
| 重试与并发 | 同位置顺序或并发确认保持位置，活动时间按等值规则更新，允许同一微秒无值变化。不同位置并发确认后落在较大位置，较旧请求不写入。不同设备的确认位置各自独立。 |
| 请求与交付证明 | 非法 JSON、重复或未知字段返回 `400 INVALID_ARGUMENT`。正常对象中缺失、无效或绑定不符的游标、篡改序号和可信位置高于 `H`，返回 `400 INVALID_CURSOR`，定位 `cursor`。额外客户端序号作为未知字段拒绝。共享 413、415 沿用既有契约。 |
| 授权变化 | 缺少有效认证或事务内会话到期、撤销、设备撤销沿用 401，账号禁用沿用 403。拒绝请求保持设备同步记录原样。 |
| 可信凭据失效 | 旧代次、同步行缺失、当前设备待重建、位置低于 `M` 返回 `410 CURSOR_EXPIRED`。新快照确认前后旧代次均被拒。即使较旧请求只会读当前位置，低于 `M` 时仍须重建。 |
| 事务失败 | 日志或设备状态异常、数据库失败或无法确认提交结果时返回统一 `500 INTERNAL_ERROR`，无成功数据。已回滚事务保持原值，提交结果未知时重试同一合法游标并查询实际位置。 |

## 14. 离线设备重建

本节约定后台离线重建。首版阈值为最近成功同步活动**严格超过 90 天**。重建复用现有快照和确认入口。

服务启动时安排首轮扫描，每轮最多 100 条、每页最多 50 条。汇报结束后一小时开始下一轮。关停时先等待任务汇报并退出，再释放连接。

### 14.1 截止时间与候选

每轮从数据库读取一次 UTC 微秒时间 `T`，以 `T - INTERVAL 90 DAY` 为截止点。本轮扫描和锁内复核共用该截止点。同步行须为 `ACTIVE`、同账号的认证设备未撤销，且 `sync_devices.last_seen_at < cutoff` 才是候选。恰好到达截止点仍保留当前基线。

`ACTIVE` 设备的同步活动时间由首次成功确认基线、推进增量确认，或等值增量确认记录。登录、刷新会话、拉取、已激活基线的确认重试以及较旧的增量确认不刷新它。空页游标可按第 13 节确认，报告设备仍在同步。

只读扫描以 `device_id` 升序分页，下一页从上一页最后设备 ID 之后开始，每页限制候选数量。候选包含所属账号、设备 ID、完整代次和观察到的同步活动时间，供事务内重新读取和比对。扫描结果只是处理线索。

### 14.2 加锁复核和状态转换

1. 后台按所属账号取得现有账号行锁，再按账号和设备 ID 锁定认证设备、同步行。复核归属、未撤销和 `ACTIVE`。完整代次与 `last_seen_at` 须仍等于扫描时观察到的值，且 `last_seen_at < cutoff`。缺行或复核条件不满足时跳过。异常数据、上下文取消或数据库失败按本项失败处理。
2. 条件仍成立时，在同一事务将同步行写为 `RESET_REQUIRED`，将 `ack_sequence` 归零，并写入服务端随机生成的完整 16 字节非零代次，须与旧代次不同。以数据库 UTC 微秒时间更新 `updated_at`，保留 `created_at` 和上次成功同步时间。外层事务提交后才计入成功。重复扫描已待重建的设备会跳过。该转换只更新设备同步状态，变更事件、账号序号和文件数据保持原样。
3. 确认与重建使用同一账号行锁。若确认先提交并把活动时间刷新到截止点或更晚，后台复核时跳过。若重建先提交，旧代次的增量确认返回 `410 CURSOR_EXPIRED`。提交后开始的拉取同样拒绝旧游标。已打开的只读事务可能交付旧视图中的页，使用其中游标发起的后续拉取或确认仍须校验当前代次。

仍为 `ACTIVE` 且未撤销的设备，即使被扫描为离线候选，也继续用其 `ack_sequence` 约束日志裁剪，直到重建提交。账号禁用或会话到期本身不解除这一约束。`RESET_REQUIRED` 设备无需保留旧位置。日后排除已撤销设备前，须先接通并验收撤销事务中的同步代次失效，确保重新登录复用设备 ID 也无法使用旧游标。日志的至少 90 天窗口仍独立生效。

### 14.3 客户端恢复和隔离验收

收到 `410 CURSOR_EXPIRED` 后停止用旧游标拉取和确认，保留本地未提交文件和待办，暂停根据远端缺项推断的删除。客户端用新幂等键创建快照，按同一快照 ID 读完并持久化完整基线或可恢复待办，提交末页凭据，再从本地保存的新基线位置开始增量。旧快照页和旧事件不能拼入新基线。恢复时重新核对本地待办与新远端状态。

| 场景 | 隔离验收结果 |
| --- | --- |
| 90 天微秒边界 | 固定数据库 UTC 时间。截止点前 1 微秒的合格设备入选，恰在截止点或晚 1 微秒的设备继续有效。 |
| 状态与分页 | 使用多个合成账号。仅读取未撤销的 `ACTIVE` 设备，按设备 ID 有界续页，跨页无重复，扫描不改任何记录。 |
| 扫描后发生确认或重建 | 在候选扫描后刷新同步活动时间，或通过快照建立其他代次。锁内复核跳过，保留新时间或新代次。仅认证活动变化的设备仍按原同步时间判断。 |
| 重建、重复与回滚 | 首次提交写入新代次、待重建和零确认位置。重复处理以及失败回滚保持相应持久状态。账号序号和事件内容原样，其他设备行原样。 |
| 游标失效与恢复 | 同账号同设备的旧增量游标在重建提交后拉取与确认均返回 410。客户端保留合成未提交内容，用新快照确认后凭新游标继续拉取，旧游标仍返回 410。 |
| 裁剪依赖 | 离线候选尚未重建提交时仍限制裁剪。已提交的待重建状态可解除设备位置约束，任一事件仍须满足自己的 90 天保留窗口。 |
