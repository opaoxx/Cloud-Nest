## 2. 架构与包结构

### 2.1 运行结构

~~~mermaid
flowchart LR
    Web[React Web] --> API[Gin HTTP]
    Native[后续桌面与移动端] --> API
    API --> Service[业务 Service]
    Service --> Repository[Repository 与事务]
    Repository --> MySQL[(MySQL)]
    Service --> Storage[对象存储适配]
    Storage --> MinIO[(MinIO)]
    Worker[后台恢复与清理任务] --> Service
~~~

首期 API 和 worker 共用一个 Go 进程。业务状态、租约与恢复条件落在 MySQL。服务重启后通过持久状态继续处理。

### 2.3 数据访问和事务约定

沿用总方案的 GORM 选择，底层驱动复用已有 go-sql-driver/mysql。第 009 小步已固定 S3 SDK 为 minio-go v7.4.1；第 019 小步固定 GORM v1.31.2、gorm.io/driver/mysql v1.6.0，底层 mysql 驱动仍为 v1.9.2；JWT 的具体版本在对应实施阶段选择并写入 go.mod/go.sum。

第 004 小步先在 repository.OpenMySQL 中复用当前驱动建立 *sql.DB 连接池，后续 GORM 装配复用此池。连接使用 utf8mb4、ParseTime=true 和 UTC 会话，不启用迁移专用 MultiStatements。启动 PingContext 最多 5 秒，也遵守调用方更短期限；失败关闭池并停止启动。连接最大寿命暂定 3 分钟，池数量沿用本方案 10/5。

第 019 小步已提供 repository.NewStore(existingPool)，复用已有 *sql.DB，不接管关闭，不执行版本探测、自动 Ping 或 AutoMigrate，并关闭原始 SQL 日志。FindLoginAccountByUsername 通过最多 5 秒、服从调用方期限的 WithContext 查询，仅选择 id/password_hash/status，参数绑定用户名且限制一条结果；models.LoginAccount 为只读三列投影，映射到 domain.LoginAccount 后返回。未命中是 domain.ErrAccountNotFound，底层失败保留错误链并返回 nil 账号，禁用状态仍返回供业务层判断。摘要不参与 JSON 序列化、不返回前端、不记录日志。当前通过测试调用查询，尚未在 main 中装配无消费者的 Store 或注册登录端点。

事务入口建议采用 Store.WithUserTransaction(ctx, actor, callback)。入口锁定 users 行，确认用户及会话有效，再向 callback 提供绑定同一个事务的 Repository 集合。回调返回错误时回滚。

用户请求的 actor 由认证中间件构造。worker 使用内部任务身份，用户归属来自数据库任务记录，并校验任务阶段和租约。后台任务在客户端退出后可继续恢复，账号被禁用时终止未完成发布并结算预占，清理工作继续遵循引用与保留期规则。

文件业务锁顺序沿用数据库方案，按 users → file_entries → stored_objects → upload_tasks → user_entry_preferences → idempotency_records 执行，同表按主键升序。认证业务采用 users → user_devices → auth_sessions。写事务中的会话有效性通过当前读复核，并与撤销流程遵循相同用户锁。

事务回调内全部使用绑定的 tx 句柄。数据库事务与对象网络调用之间用持久状态连接。[GORM 事务文档](https://gorm.io/docs/transactions.html)

持久化模型逐字段映射已存在的表名、类型、主键和索引语义。root_owner_id、active_name_key、dedup_hash 标记为只读生成列，列清单显式排除这些字段的写入。结构升级由 cmd/database 与版本迁移完成。

第 015 小步已实现 config.LoadAllowedOrigins：读取逗号分隔的 HTTP(S) 来源，规范化大小写、常规 IPv6 及默认端口，按首次出现顺序去重；显式空值、空条目、通配符、凭证、业务路径、查询和片段会报错，不回显原始输入。当前支持 ASCII 域名、标准 IPv4 和带方括号且无区域/IPv4 映射的 IPv6，国际化域名采用 punycode。main 在连接依赖前读取并记录配置。第 016 步将列表显式传入路由，按单个规范来源严格匹配；无 Origin 继续，未知/空/null/重复来源或非法预检返回统一 CORS_FORBIDDEN 403。允许的普通响应包含明确 Allow-Origin、Allow-Credentials: true，并暴露 X-Request-ID；合法预检返回无正文 204、no-store，不执行接口。所有响应按 Origin 区分缓存，OPTIONS 再按预检方法和头区分；关闭尾斜杠自动重定向，保证这类请求也先检查来源。

第 008 小步已实现 config.LoadStorageConfig，读取 provider、两个 S3 地址、bucket、access key 与 secret key。当前仅支持 local_minio；地址解析为 *url.URL，支持 HTTP/HTTPS、IPv4、带方括号的 IPv6，显式端口要求 1～65535，不允许嵌入凭证、非根路径、查询参数或片段。桶名遵循 MinIO 严格校验的基础规则，凭证非空且保持原值；错误不回显原始输入。第 009 小步已接入存储 SDK 与已有桶访问检查。后续签名必须使用目标访问地址生成，不在签名后替换 URL 主机。

storage.NewClient 使用内部地址、静态 V4 凭证和 path-style 访问创建 minio-go v7.4.1 客户端，调用 CheckBucket 在最多 5 秒内只读检查已有桶，服从调用方取消或更短期限。每个客户端独占 Transport，关闭 SDK 自动重试，保持 HTTPS 证书校验；缺桶或访问失败停止启动并记录 stage=storage，不自动创建桶。HTTP 退出后先释放存储空闲连接，再关闭 MySQL 池。CheckBucket 供后续就绪检查复用，公开地址和对象操作随对应业务功能验证。

repository.CheckSchema 在最多 5 秒内只读核对 schema_migrations，目前仅接受版本 1 的单条记录，要求 dirty=false，checksum 与程序内嵌初始 SQL 的 SHA256 一致。缺表、缺记录、未知版本、dirty、摘要不一致或读取错误均停止启动并记录 stage=schema。本检查不自动执行迁移，不逐列验证实际表结构；迁移期间仍按维护流程操作。

启动顺序为初始化固定格式的启动日志、读取并校验配置、连接数据库、核对 schema_migrations、初始化存储客户端、启动 worker、启动 HTTP。日志先于配置创建，使配置错误也能统一输出。迁移版本不兼容或 dirty=true 时停止启动。

/health/live 表示进程可响应，第 006 小步已实现 GET、无需登录、HTTP 200 和 {"status":"ok"}，请求处理不访问数据库或存储。第 010 小步已实现 GET /health/ready：无需登录，两项依赖检查共享最多 5 秒，全部通过返回 200 与 {"status":"ready"}，任一失败、超时或取消返回 503 与 {"status":"not_ready"}；设置 Cache-Control: no-store，不回显底层错误或凭证。HealthService 依次调用 MySQL PingContext 和存储 CheckBucket，失败立即返回，故障恢复后下次请求重新检查。/ping 保留现有响应，便于开发工具继续使用。路由由 http.NewRouter 创建，具体请求处理位于 http/handler，启动入口负责依赖装配与监听。

数据库池初始 MaxOpenConns=10、MaxIdleConns=5，SQL 请求超时初始为 5 秒。JSON 请求体限制 1 MiB。第 017 步已提供 binding.ReadJSON(ctx, &requestDTO) bool，由需要 JSON 的 Handler 显式调用；现有三个系统 GET 不读取正文。只接收未压缩的 UTF-8 application/json，按实际字节受限读取，再解析单个对象并拒绝未知字段、类型错误或多段 JSON。输入错误返回 INVALID_ARGUMENT 400、REQUEST_BODY_TOO_LARGE 413 或 UNSUPPORTED_MEDIA_TYPE 415，沿用统一错误结构和请求 ID，不回显原始输入。必填和业务规则由后续 DTO 校验处理；失败时 Handler 必须立即 return，禁止使用部分解析的数据。HTTP ReadHeaderTimeout 初始为 5 秒，小文件传输使用独立的请求总时限，初始为 5 分钟。退出时先停止领取任务，等待在途请求和 worker 最多 30 秒，再关闭资源，剩余租约由重启恢复处理。

第 007 小步已使用标准库 http.Server 管理 Gin 路由，ReadHeaderTimeout=5 秒。main 将中断信号转换为上下文取消，传递给启动检查及 http.Serve；HTTP 使用独立的 30 秒 Shutdown 期限等待在途请求，失败时 Close 强制关闭并返回错误。Serve 返回后关闭 MySQL 池。正常中断退出码为 0，真实配置、依赖或 HTTP 运行/关闭错误为 1。worker 与升级连接的退出处理随其引入补充。

## 4. 统一 HTTP 契约

### 4.1 数据类型

- 业务路由统一位于 /api/v1。
- 用户、设备、文件、任务 ID 和 revision 使用十进制字符串。
- 字节数使用 JSON number，服务端限制在 JavaScript 安全整数范围内，当前配额和文件上限满足该范围。
- 时间输出 UTC RFC 3339，最多保留数据库的六位小数。
- 可空值显式返回 null。列表没有下一页时 next_cursor 返回 null。
- 前端展示名、扩展名、分类由 DTO 提供。Storage 的对象键及凭证由服务端持有。
- 请求带 X-Request-ID 时仅接受单个标准 36 字符 UUID v4（RFC 4122 variant），合法值规范成小写，否则生成新 UUID v4，不因标识无效拒绝原请求。第 011 小步已将最终 ID 写入标准请求上下文及请求/响应头，多个同名头或合并值同样替换；第 012 小步已让统一请求日志读取同一 ID，后续业务响应沿用该 request_id。

业务接口成功响应使用 data 与 request_id，失败响应使用 error 与 request_id。HTTP 状态码与业务错误同时表达结果。系统探测接口 /ping、/health/live 与 /health/ready 直接返回各自约定的简单 JSON，具体见 api/openapi.yaml。

第 013 小步已实现 NoRoute 的统一 404：error.code=ROUTE_NOT_FOUND、message=未找到匹配的接口、details=null，request_id 与上下文、响应头及日志一致；Content-Type 为 application/json，Cache-Control 为 no-store。ErrorResponse/ErrorDetail 定义在 http/dto，未匹配处理位于 http/handler/not_found.go，不访问依赖或回显请求内容。普通未注册方法沿用 404；第 016 步关闭尾斜杠自动重定向，并对来源与预检优先执行 CORS 策略。HEAD 不返回正文；其他状态错误逐小步接入。共享契约位于 components.responses.RouteNotFound，不添加虚构的通配 API。

第 014 小步已实现普通异常恢复的统一 500：响应未提交时，返回 INTERNAL_ERROR、固定提示、details=null 和当前 request_id，并清理冲突的待发送长度/编码头，设置 JSON 与 no-store。响应已提交时仅停止处理，保留实际状态、头和正文。Recovery 禁止原始转储，对交给回调的普通异常只设置 recovered_panic=true；完成日志使用 ERROR 并保留实际 status。共享契约为 components.responses.InternalError，三个系统 GET 操作均引用此 500；网络断连等特殊情况沿用 Gin 逻辑，没有增加生产异常测试接口。

### 4.2 认证与幂等头

普通业务请求使用 Authorization: Bearer access_token。创建目录、重命名、移动、回收、恢复及创建上传等业务写请求要求 Idempotency-Key，建议采用 UUID。

完成与取消上传依赖 task_id 和持久状态实现幂等。收藏使用 PUT 设置明确布尔状态。访问时间记录采用可合并更新。

幂等键绑定用户、版本化操作、资源 ID 与规范化请求摘要。同键同请求返回已记录结果，同键不同请求返回 409。结果中保存稳定 ID，临时签名 URL 在重新鉴权后签发。记录保留至少 7 天，客户端跨保留窗口重试时先查询已有资源。

## 6. 登录与会话流程

### 6.1 登录

1. 对 JSON、用户名、密码长度和安装 UUID 做格式校验。
2. 使用 bcrypt 验证已有业务账号，失败统一返回认证失败信息。
3. 检查用户状态，按 user_id 与 installation_id 找到或创建设备。
4. 在用户事务中创建 auth_sessions，随机生成 Refresh Token 并只保存 SHA256。
5. 签发 15 分钟 Access Token，返回用户、真实根目录与当前设备。
6. 节流更新设备及会话 last_seen_at，避免每次请求都写入时间。

第 020 小步已提供 service.VerifyPassword(passwordHash, rawPassword) (bool, error)：先检查本项目支持的标准 60 字符 $2a$/$2b$/$2y$ 摘要和成本 4～14，再验证原始候选密码。匹配返回 true/nil，不匹配及无效候选（有效摘要下为空、非 UTF-8 或超过 72 字节）返回 false/nil；摘要格式/成本不受支持或其他 bcrypt 错误返回固定 domain.ErrInvalidPasswordHash，不携带敏感内容。当前种子账号成本为 12，不改变已有摘要。方法同步调用现有 bcrypt.CompareHashAndPassword，不重新生成摘要、不修改密码，也不承诺 context 可中断计算。此内部摘要错误不直接作为客户端凭证失败；登录服务的查询/状态/凭证错误编排随后实现，当前不注册登录路由。

第 021 小步已提供 CredentialService.Authenticate：注入现有账号查询方法，绑定 VerifyPassword，统一账号不存在/密码错误为 domain.ErrInvalidCredentials；未命中也使用固定非账号摘要执行一次成本 12 的比对，且不论是否匹配都拒绝认证，以减少明显快速失败差异，不承诺恒定耗时。密码匹配后才判断 ACTIVE/DISABLED，禁用返回 ErrAccountDisabled，未知状态、零 ID 或意外 nil 数据返回 ErrInvalidAccountData。成功仅返回 VerifiedAccount.ID，不携带摘要，不创建会话。查询故障保留错误链，摘要异常仍按内部故障处理；查询和同步比对前后检查请求取消，取消后不返回身份。当前仅测试装配，未注册 HTTP 登录路由；来源策略已在第 022 步实现，失败限流核心见第 023 步，HTTP 接入仍按后续小步进行。

JWT 采用固定算法 HS256，校验签名、issuer、audience、sub、sid 和 exp。签名密钥持久化，重启继续使用已有密钥。普通业务中间件查询会话和用户状态，关键写事务再复核撤销状态。

登录限流首期使用有界内存记录，按来源 IP 与用户名分别计数，初始每分钟各 10 次失败尝试。清理过期记录并限制总条目数。第 023 小步已提供 LoginFailureLimiter.Begin：每个维度使用首次预留起 60 秒的固定窗口，失败数加在途预留最多 10；同时检查并预留两维，避免并发穿透。返回完成回调、建议等待或输入错误，完成回调幂等；只对 ErrInvalidCredentials 结算失败，其他结果释放预留但不清除已有失败。最多 4096 条有界键记录，容量不足拒绝而不驱逐未过期计数；按需清理到期失败并保留在途，无失败/在途的空记录即时释放。IP 使用 netip.Unmap 统一映射表示，用户名只接受规范小写 ASCII；可信 IP 提取与 HTTP 429/Retry-After 在下一步接入。该核心仅限单进程，重启清空，不是任意滚动 60 秒的严格上限；在途未结束时等待值不保证到期就可放行。

### 6.2 Web 与原生凭证交付

Web Access Token 存于页面内存，Refresh Token 通过 HttpOnly、SameSite=Strict Cookie 交付，路径限定为 /api/v1/auth。本机 HTTP 开发环境使用对应的 Cookie 配置，HTTPS 部署启用 Secure。

Web 刷新、登录和退出请求检查 Origin 白名单，并要求自定义 X-CloudNest-Client: web 请求头。凭证型 CORS 使用明确 Origin，跨站预检被拒绝。允许的请求头包括 Authorization、Content-Type、Idempotency-Key、X-CloudNest-Client 和 X-Request-ID。第 016 步已实现全局 CORS，预检支持 GET、HEAD、POST、PUT、PATCH、DELETE、OPTIONS；合法预检仅表示策略许可，不验证具体路径是否实现。不带预检方法头的 OPTIONS 沿用普通路由，显式空或非法的预检头拒绝；不设置预检缓存时长。第 022 小步已提供独立 LoginSourcePolicy：登录正文 client_type 与单个 X-CloudNest-Client 必须精确相同；web 另需单个白名单 Origin，native 则必须无 Origin。策略放在 DTO 校验后、凭证查询前，违规返回 CLIENT_SOURCE_FORBIDDEN 403，不回显请求内容。全局 CORS 先拒绝的未知 Origin 仍为 CORS_FORBIDDEN；合法预检不进入登录来源检查。当前通过测试专用入口验证，不改变系统 GET；登录、刷新与退出的实际 Handler 按对应步骤接入。

原生客户端登录要求 X-CloudNest-Client: native 且不带 Origin；若使用自动附带 Origin 的 WebView 网络层，应改用匹配方案的原生 HTTP 通道，不能直接跳过检查。该声明不证明程序身份，仍需验证凭证。原生客户端通过 JSON 获得 Refresh Token 并保存在系统安全存储。刷新请求在 JSON 中提交令牌，原生模式使用令牌载荷交付，Web Cookie 路径仅由 Web 模式处理。出现未知 Origin 的浏览器请求统一拒绝。

每个客户端对刷新执行 single-flight。轮换使用旧摘要和 token_generation 条件更新，成功后旧刷新值失效。刷新响应丢失时重新登录。退出撤销会话，并清理 Web Cookie 或原生本地凭证。

## 7. 目录和偏好规则

名称规则与数据库方案共用样例，按 NFC → case folding → NFC 生成 UTF-8 名称键。显示名最多 120 个 UTF-16 代码单元，归一化键最多 768 字节。空名、路径字符、控制字符及保留设备名在 Service 中校验。

创建目录、重命名和移动遇到活动名称冲突返回 NAME_CONFLICT。上传和恢复采用后缀命名策略，扩展名保留在末尾，必要时截短基名以满足长度上限，结果返回最终名称。

每个文件或目录操作校验 user_id、自己的生命周期、全部祖先、父目录类型及权限。移动额外验证目标不在自身子树，深度最多 32，目标移动后的后代深度也需满足限制，操作子树最大 10000 项。

expected_revision 在持锁事务中比对。内容、名称、位置或回收状态变化时 revision 加一并更新时间。收藏与访问记录写入偏好表，文件 revision 保持其业务修改含义。

目录列表读取使用一致性数据库快照完成父链与条目查询。授权下载的权限判断对应签名时刻，签名 URL 有效期内持有者可以读取对应不可变对象。

## 8. 小文件上传闭环

### 8.1 创建与接收

1. POST /uploads 校验名称、大小、目标目录和来源设备，在用户事务中检查配额并预占完整文件大小。
2. 创建 STAGING 对象记录及 SINGLE 上传任务，生成随机对象键，任务进入 UPLOADING。幂等结果与任务同事务写入。
3. 客户端向 content_path 发送原始文件流。服务端在用户事务中领取该任务租约，递增 lease_version，持有有效租约的并发请求返回 UPLOAD_BUSY。
4. 请求体流式写入应用临时文件，同时计算 SHA256 和实际字节数。限制为声明大小加一个检测字节，并受 16 MiB 上限及传输总时限约束。
5. 核对实际大小，客户端提供 sha256 时同时比较。随后从已稳定的临时文件写入当前 staged_object_id 对应的对象键。
6. 存储写入返回后，以 task_id、status、lease_version 和 staged_object_id 为条件进入 VERIFYING，释放接收租约并交给校验 worker。
7. PUT 返回 202，前端展示“校验中”，轮询任务结果。

临时文件使用应用专属目录与随机尝试标识，文件名由服务端生成。初始最大并发接收数为 3，临时区容量上限为 128 MiB。失败和退出后通过归属清晰的临时文件清理流程回收空间。

接收过程使用 http.MaxBytesReader 等手段限制实际读取量，并将请求取消传递给临时文件处理和存储调用。[Go HTTP 请求体限制](https://pkg.go.dev/net/http#MaxBytesReader)

### 8.2 上传重试与不可变写入

首次写入使用任务当前的 staged_object_id。任务进程崩溃或响应丢失后，恢复流程先检查该对象是否完整存在，存在且大小、哈希符合时继续校验发布。

确需重新接收内容时，在用户事务内取得新租约，创建新的 STAGING 对象并更新 staged_object_id，旧对象进入 ORPHANED。新尝试拥有独立对象键，旧请求的迟到写入只影响旧尝试的对象。所有后续数据库回写必须匹配当前租约和对象 ID。

任务在一个时间点仅保留一个当前 staged_object_id。已替换的暂存对象通过自身状态与清理时间继续管理。签名及长期对象键保持不可复用原则。

### 8.3 校验、去重与发布

校验 worker 领取 VERIFYING 租约，在事务外读取存储对象并重新计算大小和 SHA256。校验结果只对当前 staged_object_id 及租约版本有效。

发布事务依次完成以下动作。

1. 锁定用户，复核账号、任务、目标目录和祖先状态。
2. 按同用户哈希与大小查找 READY 对象。存在可复用对象时引用它，暂存副本进入 ORPHANED，否则把本次对象推进 READY。
3. 在用户锁内选择可用上传名称，生成符合长度限制的后缀。
4. 创建 FILE 目录项，写入对象 ID、大小快照、来源设备和内容时间。
5. 将任务 reserved_bytes 转入 used_storage，预占归零。
6. 写入 published_object_id、result_entry_id、resolved_name、completed_at，任务进入 COMPLETED。
7. 新建内容引用的对象清空 unreferenced_at 与 gc_after。

目标目录失效时终止发布并释放预占，返回 TARGET_UNAVAILABLE。同名上传按批准的后缀策略处理。校验失败进入 FAILED 并释放预占，暂存内容进入延迟清理。

### 8.4 取消与幂等完成

完成请求只推动已有任务。UPLOADING 且内容尚不完整时返回 TASK_NOT_READY，VERIFYING 返回 202，COMPLETED 返回已保存的结果 ID。

取消请求将可取消阶段转入 CANCELLING，随后终结为 CANCELLED 并将 reserved_bytes 归零。过期流程对应 EXPIRING → EXPIRED。完成、取消和过期在同一用户锁及任务条件更新下竞争，终态重试复用已记录结果。

临时网络失败记录 next_attempt_at 和 last_error_code，任务保持可恢复状态。目标失效、大小不符、校验失败等业务错误按明确规则结束任务。

## 9. 下载与预览

POST /entries/{id}/download 验证会话、文件归属、祖先可见性和 expected_revision，再确认对应物理对象为 READY。存储对象缺失或不可用时返回明确错误并记录核对任务线索。

签名固定到不可变 object_id 和对象键，有效期初始为 15 分钟，响应包含对象身份、版本、字节数和已验证 SHA256。URL 过期后需要重新鉴权，同一下载任务继续绑定原对象。原内容已经无权访问时结束续传。

首期下载采用短期 S3 GET URL，存储提供 Range 能力。客户端对 200、206、416 和对象身份变化分别处理。前端通过 download 返回的名字生成下载行为，文件名使用规范 Content-Disposition 编码。

预览初期覆盖已校验 MIME 的常见栅格图片和大小不超过 2 MiB 的纯文本。纯文本由界面转义渲染。浏览器可支持的 PDF 和视频预览在对应前端阶段验证后开放。其他格式提供下载。

purpose=download 或成功授权的预览访问记录 last_opened_at，最多每 60 秒合并一次。该时间表示获得访问授权的时刻。

## 10. 回收站与永久清理

### 10.1 回收与恢复

回收将被选根项改为 TRASHED，保留 parent_id、对象引用和配额占用。后代在所有正常列表及授权流程中按祖先状态隐藏。

恢复在用户锁内确认原父目录是否可访问。有效则恢复至原位置，失效则选择真实根目录。名称冲突自动增加后缀，响应给出实际位置和名称。文件偏好保留，恢复后重新进入有效收藏和最近使用候选。

批量操作先移除选择集合中已被选中祖先覆盖的后代。每个顶层项独立返回结果，部分失败时保留准确状态。

### 10.2 永久清理

清理请求验证预检摘要、expected_revision、归属和范围，原子标记 PURGING。该状态让子树立即不可访问，返回 202 和稳定的根目录项 ID 供查询。

worker 每次在用户事务中选取最多 100 个可处理叶子。对每个尚未 PURGED 的 FILE 释放逻辑空间、清空 object_id、删除偏好并写入 purged_at。DIR 在后代处理完成后终结。事务回滚保持该批原状，重启后继续扫描持久状态。

被清理目录内此前已独立回收的后代计入预检范围。PURGED 墓碑按数据库保留期和引用约束进行后续清理。

### 10.3 对象 GC

逻辑引用释放后，在用户事务中检查对象是否仍被正常文件、回收站、清理中后代、非终态任务或后续历史版本引用。确认失去最后引用时写入 unreferenced_at，gc_after 设为 7 天后。

到期 worker 再次锁定用户和对象，检查当前全部有效引用并条件转为 DELETING。随后在事务外删除存储对象，成功或确定对象已不存在后标记 DELETED。失败保留 DELETING 并周期重试。

READY 或 ORPHANED 对象状态改变后，dedup_hash 由数据库生成列更新。新引用只能指向 READY 对象，并与 GC 使用相同用户锁，避免新引用和删除交错。

## 11. 后台任务、重试与观测

### 11.1 首期任务安排

| 任务 | 初始频率与并发 | 持久依据 |
|---|---|---|
| 上传校验与恢复 | 每 5 秒扫描，1 个校验 worker | upload_tasks 状态、next_attempt_at、lease_version |
| 上传取消与过期 | 每 30 秒扫描，最多 100 项 | status、expires_at、reserved_bytes |
| 回收站到期标记 | 每小时扫描，最多 100 个根项 | TRASHED 和 deleted_at |
| 子树永久清理 | 每 5 秒扫描，每事务最多 100 项 | PURGING/PURGED |
| 孤儿对象与 GC | 每分钟扫描，初始并发 1 | status、unreferenced_at、gc_after |
| 会话及幂等记录过期清理 | 每小时小批执行 | expires_at、revoked_at |
| 配额核对 | 每日及恢复维护窗口 | 未 PURGED 文件、保留版本与任务预占 |
| 临时文件回收 | 启动时及每小时 | 应用目录内的归属标识和任务状态 |

任务频率均可配置。目录批处理只进行短数据库事务，同账号锁协调并发执行。涉及长存储 I/O 的上传任务领取租约，初始期限 60 秒，每 20 秒续约，写回时要求租约仍有效且版本匹配。

对象 DELETING 状态充当清理意图。物理删除按固定对象键幂等执行，多个恢复执行者即使重叠也只能处理同一不可变对象。

### 11.2 重试边界

瞬时网络失败采用有限指数退避，初始 1 秒，最高 30 秒，每轮最多 5 次。超过本轮次数后写入下次恢复时间，由持久任务再次调度。

数据库死锁只重试包含纯数据库动作的完整事务回调，初始最多 3 次。幂等键及事务结果同时处理，外部存储操作依赖持久阶段，重试时重新核对其状态。

客户端断连取消当前接收和短请求。已持久化的校验、取消及发布恢复由 worker 接管，客户端可以通过任务 ID 继续查询。

### 11.3 日志与状态

日志至少包含 request_id、user_id、session_id、task_id、object_id、阶段、耗时和错误码。密码、Access/Refresh Token、签名 URL 查询参数和文件内容从日志排除。

第 012 小步已实现 HTTP 完成日志，字段为 request_id、method、path、status、duration_ms，并沿用时间、级别与服务名；其他业务字段随后续功能接入。NewRouter 接收入口日志对象，显式采用 RequestID → RequestLog → Recovery → CORS 顺序；Recovery 禁止原始请求和 panic 转储，日志在恢复完成后记录最终状态。普通请求的 2xx/3xx 为 INFO、4xx 为 WARN、5xx 为 ERROR；第 014 小步增加普通恢复异常的 recovered_panic=true 标记，即使响应已提交而实际 status 小于 500，仍使用 ERROR。path 仅取 URL.Path，不记录查询、请求头、正文、c.Errors 或 panic 载荷；替换默认文本访问日志，避免重复输出。

首期记录请求错误率、数据库耗时、任务积压、校验耗时、重试次数、临时空间、GC 失败和配额差异。关键任务失败能在上传结果或运维日志中定位。

开发模式只信任直接来源，部署反向代理时显式配置可信代理和 Origin。JSON 参数和错误响应保持统一脱敏规则。

## 12. 前端接入约定

### 12.1 前端数据适配

建议增加 api/http.ts 处理认证、刷新和统一错误，api/drive.ts 封装业务接口。Demo 数据和真实 API 通过明确的数据模式配置选择，界面状态由对应数据源驱动。

| Demo 字段或行为 | API 适配 |
|---|---|
| id 字符串 | 直接使用服务端字符串 ID |
| 根层 parentId=null | 请求前映射为 /me.root_entry_id，普通子目录使用真实 ID |
| kind | DIR 映射 folder，其余由 category 映射小写文件类别 |
| size | 对应 size_bytes |
| modifiedAt | 将 modified_at 解析为展示时间 |
| device 展示名 | 对应 source_device.name |
| starred | 对应偏好字段，操作调用 PUT /star |
| deletedAt | 对应 deleted_at，页面同时处理 status |
| preview | 按需调用 download 接口取得短期 URL |
| 上传进度 | 浏览器发送进度加服务端任务阶段 |
| 最近使用 | 使用 recent scope，按 last_opened_at 排序 |

后端根目录本身由 /me 返回，目录列表展示根目录中的条目。前端保存真实 root_entry_id，避免把所有根层文件按数据库 NULL parent_id 查询。

### 12.2 登录与页面状态

首次接入增加登录界面，使用已初始化的业务 root 账号。页面刷新时通过 Web 刷新凭证恢复会话，再获取 /me 和根目录。

API 返回 401 时由单一刷新请求协调重放，写请求保持原幂等键。刷新失败清理会话并回到登录。接口异常进入明确的错误或重试状态。

列表页面支持加载中、空列表、加载失败和部分批量失败。删除完成后刷新列表及空间信息。上传阶段为 VERIFYING 时显示“校验中”，COMPLETED 后使用 result_entry_id 读取真实文件并更新列表。

浏览器上传进度优先用 XMLHttpRequest 的上传事件，控制接口采用 fetch。SINGLE 暂停在首期表现为中止当前发送并保留任务，继续时整文件重传。Multipart 阶段才提供按分片续传。

### 12.3 本机开发访问

建议 Vite 将 /api 代理到 127.0.0.1:18081，使 Web Cookie 和控制接口采用同一页面来源。后端仍校验前端 Origin 白名单，避免开发代理放宽业务授权。

MinIO 下载属于独立端口来源，配置仅覆盖已验证用途所需的 CORS。分片直传上线时再验证 PUT、校验请求头和 ETag 暴露。

## 14. 本次评审关注项

1. Go 单体服务采用 Handler → Service → Repository 与 Storage 的分层，持久任务随同一进程运行。
