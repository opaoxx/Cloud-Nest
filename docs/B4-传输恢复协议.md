# B4 传输恢复协议（评审稿）

基线为 B3 收尾提交 `80e764d`。本稿细化整体方案第 6、7、12.2、13.1 节、已批准后端方案第 13 节和数据库方案中 `upload_tasks`、`upload_parts` 的约定。交付范围为大文件原生 Multipart、续传、发布恢复和同账号内容复用。Wails、Flutter 和同步有各自的后续阶段。

## 1. 分片计划与客户端恢复

`0～16 MiB` 继续走 B3 的 `SINGLE`。超过 16 MiB 由后端选用 `MULTIPART`，初始上限 50 GiB，同时受已验收的存储能力约束。超过上限在预占前以 `413 FILE_TOO_LARGE` 拒绝。Multipart 的 `sha256` 为必填的整文件摘要。客户端在创建请求前持久化服务器、账号、目标、创建幂等键和源身份，收到回执后保存任务 ID、分片计划及逐片上传回执。退出或重启后重新读取源文件，大小及 SHA-256 都一致才继续。签名 URL 过期后重新签发。

- 初始分片为 16 MiB。以 MiB 为单位向上取整增大到可容纳总文件且 `part_count ≤ 10000` 的最小尺寸，同时检查存储端单片及总大小上限。后端检查配置和算术边界，在创建时持久化计划。
- 分片编号从 1 起。第 `n` 片偏移为 `(n-1) × part_size`，大小取 `min(part_size, size_bytes-offset)`。恰好整除时最后一片是完整分片。50 GiB 按 16 MiB 计算为 3200 片。
- 客户端初始并发 3，可配置为 1～5，同一编号同一时间仅发送一次。网络中断、限流及临时服务错误有界退避，过期签名先重签。源文件不一致、无法读取或临时副本可用空间不足时暂停并交付明确原因。低磁盘用例覆盖需要落盘的客户端临时副本和 B3 兼容链路，B4 服务端校验流式读取目标对象。

例如 `41943041` 字节（40 MiB 加 1 B）分为 `16777216`、`16777216`、`8388609` 字节。若重启后前两片回执仍和存储端匹配，只补送第 3 片。本地回执丢失或与存储端不符时，将该片视为未确认，重新上传并保存新回执。

## 2. API 草案

全部应用接口沿用 Bearer 授权、现有 Origin 策略、`data`/`error` 与 `request_id` 结构和 `no-store`。任务归属取自认证账号，同账号设备可以继续原任务。任务及目录 ID 使用标准十进制字符串。跨账号或缺失任务统一 `404 UPLOAD_NOT_FOUND`。

| 接口 | 输入和响应 | 约束 |
|---|---|---|
| `POST /api/v1/uploads` | 继续接收 `parent_id`、`name`、`size_bytes`、`sha256` 及 `Idempotency-Key`。Multipart 的整文件 `sha256` 必填，`201` 含 `task`、`upload_mode: MULTIPART`、`part_size_bytes`、`part_count`、`expires_at`，初始任务为 `CREATING` | `SINGLE` 沿用原 `201` 快照和 `content_path`。首次创建时固定分片计划，快照与任务和预占一起提交。同键同参数重试交付初始快照，任务查询交付实时状态和截止时间 |
| `GET /api/v1/uploads/{id}` | 保留现有公开任务快照，用于查看 `CREATING`、`UPLOADING`、校验、失败或发布结果 | 创建回执丢失可用原创建键找回计划。任务查询和创建快照均不交付 `storage_upload_id` 字段 |
| `POST /api/v1/uploads/{id}/part-urls` | `parts` 为 1～20 项，每项包含 `part_number` 和 `sha256`（64 位十六进制）。可选 `renew_if_expires_at`。返回 `200`，`data.expires_at` 为当前任务截止，`data.parts` 每项包含编号、`size_bytes`、`url`、`required_headers` 和 `url_expires_at` | 仅接受处于 `UPLOADING`、未过期、无正在核对完成的租约的任务。编号按计划校验且不得重复。URL 仅授权对指定会话的该编号执行 `PUT`，校验头随签名绑定。初始有效期 5 分钟，且不超过任务期限 |
| `GET /api/v1/uploads/{id}/parts` | `200` 返回 `data.part_size_bytes`、`data.part_count`、`data.parts`，逐片提供 `part_number`、`size_bytes`、`etag` 和 `checksum_sha256`（Base64）。按编号升序返回本次核对的全部可用分片 | 未到期的 `MULTIPART/UPLOADING` 且已有存储会话才可核对。长度与计划不符的分片从结果省略。存储读取或分页异常返回 `503 STORAGE_UNAVAILABLE`。客户端先核对源文件，再依据本地和存储回执补传缺失或不匹配的片 |
| `POST /api/v1/uploads/{id}/complete` | Multipart 在 `UPLOADING` 提交 `parts: [{ "part_number": 1, "etag": "…" }]`，计划中的每个编号须恰好出现一次。核对并提交完成快照后返回 `202`。`COMPLETING`、`VERIFYING` 返回 `202`，`COMPLETED` 返回 `200` 及同一 `result_entry_id` | `SINGLE` 沿用无正文状态确认。Multipart 的完成幂等以任务 ID 和已提交快照为依据，已受理的重试可省略正文。任务回到 `UPLOADING` 修复后，下一次完成请求提交新回执 |
| `POST /api/v1/uploads/{id}/cancel` | 沿用无正文请求，`202` 表示 `CANCELLING` 已提交，`200` 交付实际终态 | 有执行租约时返回 `409 UPLOAD_BUSY`，尚未开始取消且已到期或正在过期收尾时返回 `409 TASK_NOT_READY`。后台核对会话及对象后，提交 `CANCELLED` 与预占返还。发布先提交则返回 `COMPLETED` 和原文件 ID |
| `POST /api/v1/files/reuse` | `parent_id`、`name`、`size_bytes`、`sha256` 和 `Idempotency-Key`。`201` 返回新 `ACTIVE/FILE` 条目的创建快照 | 仅复用同账号仍有可见逻辑引用、摘要与大小均匹配的 `READY` 对象。新文件的完整大小计入已用空间。同键同参数重放原结果。无可用引用统一返回 `404 REUSABLE_CONTENT_NOT_FOUND`，客户端可继续走普通上传 |

显式续期沿用授权、账号锁及配额校验。`renew_if_expires_at` 绑定客户端最后看到的截止时间，格式沿用 UTC 微秒。仅当前未过期、状态及租约允许、全额预占仍有效且 `used + reserved ≤ quota` 时可以续期。新截止为数据库当前时间加配置有效期（初始 24 小时），若计算结果较早则保持原截止。旧时间参数返回 `409 TASK_NOT_READY`，重读当前任务后决定是否续期。普通查询、签发和完成重试不自动续期。

表中的新增字段和错误为草案。`part-urls` 将分片 SHA-256 编码为 Base64，通过签名固定 `x-amz-checksum-sha256`。客户端按返回头发送，不附带应用 Bearer 或 Cookie。Web 由固定长度 `Blob` 发送，浏览器生成 `Content-Length`。后端在交付签名之前复查任务有效、会话匹配及核对租约。固定 MinIO 镜像需用隔离桶实测签名绑定长度、错误摘要拒绝、CORS `PUT` 预检、ETag 暴露、ListParts 回执和版本化完成。若头或长度约束无法落实，需评审调整方案后再开放直传。应用日志不记录查询串、签名 URL、存储凭据或原始存储错误。

现有 JSON 上限为 1 MiB。草案将当前存储适配的回执 ETag 规范化为去除成对外引号后 1～64 个 `A–Z a–z 0–9 . _ : -` 字符，保留大小写。10,000 片且每个 ETag 均为 64 字符的紧凑完成请求为 948,905 B。回执按不透明标识比较，此格式须随目标镜像实验验证。原始存储字段的数据库容量沿用已批准方案。

### 错误与重试

| 场景 | HTTP 或任务结果 | 客户端行为 |
|---|---|---|
| 字段不合法、编号越界或重复、首次完成缺少回执 | `400 INVALID_ARGUMENT`，`details.field` 定位字段 | 修正输入 |
| 超过文件上限或预占失败 | `413 FILE_TOO_LARGE` 或 `507 QUOTA_EXCEEDED` | 查看上限或空间，不循环重试 |
| 任务阶段不符、已经到期或执行租约冲突 | `409 TASK_NOT_READY` 或 `409 UPLOAD_BUSY` | 查询同一任务，按实际阶段等待或重新创建 |
| 请求完成时缺片、片长错误或回执与存储端不符 | 首次完成核对返回 `409 UPLOAD_PARTS_MISMATCH`，`details.part_numbers` 给出有界列表（最多 20 项）。完成 worker 发现可修复失配时保存同一公开码 | 重新查询分片，补传受影响片，使用新回执再请求完成 |
| 存储调用暂时失败或结果未知 | 入口可返回 `503 STORAGE_UNAVAILABLE`，后台保留阶段和下一次重试时间 | 先查询业务任务，继续使用原任务或原创建键 |
| 存储会话失效且确认没有完成的对象 | `FAILED`，查询中的错误为 `UPLOAD_SESSION_LOST` | 确认原任务已释放预占后重新创建 |
| 已完成对象的整文件字节数、哈希不符，或目标目录失效 | `FAILED`，分别为 `BODY_SIZE_MISMATCH`、`CHECKSUM_MISMATCH`、`TARGET_UNAVAILABLE` | 停止该任务，按原因重新选择内容或目标 |

## 3. 核对与完成的事务边界

~~~text
CREATING → UPLOADING → COMPLETING → VERIFYING → COMPLETED
                          ↓ 确认尚未完成且分片回执已变化
                      UPLOADING
~~~

1. **创建及初始化。** 应用层按既有规范化字段处理幂等。同一创建操作和键保留八天，SINGLE 沿用既有摘要及响应编解码。Multipart 使用包含上传模式和整文件摘要的固定编码，同键切换声明仍判定冲突。账号锁内复查会话、设备、可见目标目录、深度及配额，创建唯一 `STAGING` 对象键和 `CREATING` 任务并预占全额。后台按数据库时间领取租约，事务外创建 Multipart，回写按任务、对象、阶段、期限和 `lease_version` 条件匹配。提交会话 ID 后才进入 `UPLOADING`，同任务的原计划和键持续复用。
2. **核对分片。** 服务端使用保存的桶、不可变对象键和会话 ID 获取 `ListParts`，每页处理截断标识和严格递增的游标，核对归属、编号、无重复、各片预期大小及整段范围。提前结束或游标异常整轮失败。返回完整核对结果前复查任务阶段、期限和会话，避免交付属于旧会话的快照。已有同编号回执仅在最新存储回执也匹配时有效。 [S3 ListParts](https://docs.aws.amazon.com/AmazonS3/latest/API/API_ListParts.html) · [S3 UploadPart](https://docs.aws.amazon.com/AmazonS3/latest/API/API_UploadPart.html)
3. **持久化完成意图。** 首次完成在账号事务中领取 `UPLOADING` 核对租约，停止签发新 URL。事务外用完整 `ListParts` 验证客户端上传回执及连续编号、片长和总大小。全部匹配时，在同一事务按有效租约和原会话写入 `upload_parts` 完成快照、转为 `COMPLETING` 并释放核对租约，再返回 202。核对失败保留 `UPLOADING` 并释放租约。已提交的快照在 `COMPLETING` 时冻结。客户端回执提供完成列表，存储清单提供独立核对。 [S3 Multipart 上传流程](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html)
4. **完成存储对象。** 后台为 `COMPLETING` 领取新租约，复查保存的回执与存储现状，用固定会话和顺序回执完成。以 SDK 解码的成功对象结果为准，同时保存后续读取必需的版本定位。先前签出的 URL 在有效期内仍可能有请求在途。若分片被替换导致确定性的 ETag 失配，只有明确对象未完成且原会话仍可用时才在条件更新下回到 `UPLOADING`，清除旧完成快照并允许修复。结果未知时保持 `COMPLETING`，按第 4 节先核对，避免把成功完成误当成缺片。 [S3 CompleteMultipartUpload](https://docs.aws.amazon.com/AmazonS3/latest/API/API_CompleteMultipartUpload.html) · [S3 预签名有效期](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html)
5. **校验和发布。** 保存确认的版本和 ETag 后推进 `VERIFYING`，保留任务的原声明大小和摘要。校验 worker 流式读取该版本，将整文件字节数及 SHA-256 与声明比对。发布事务在账号锁内复查租约、目标目录和引用，按现有规则确定重名后缀、选择同账号 `READY` 对象，创建逻辑文件，`reserved → used`，保存结果 ID 并提交 `COMPLETED`。每个目录项独立计入逻辑空间。只有提交后的结果 ID 用于目录刷新和正常签名下载。暂存副本按已有宽限规则进入 GC。

## 4. 失败窗口与收尾

所有存储 I/O 位于数据库事务外。领取及续约沿用数据库时钟和 `lease_version`。版本失配的旧 worker 无权回写发布结果，可能已经发生的存储副作用由新 worker 核对。

| 故障窗口 | 处理与状态 |
|---|---|
| 创建存储会话超时，或收到会话 ID 后写库失败 | 同一任务保持 `CREATING`，预占不重复。保留未关联会话的宽限期，按应用对象前缀核对后续清理。仅数据库已绑定的会话可签发或完成。孤儿扫描分批检查会话、对象和有效创建租约，只中止明确未关联且超过宽限期的会话 |
| 存储完成请求或响应丢失 | 用任务唯一键核对 `Head`、原会话及存储版本。确认完成时保留其版本并进入 `VERIFYING`。只有确认尚未完成且原会话有效时，才用同一会话及持久化回执恢复完成。`NoSuchUpload` 后继续确认；在完成操作已结束且会话、对象均确认不存在时，进入 `FAILED` 并释放预占。存储结果仍不确定时保留重试 |
| 已完成存储但数据库校验/发布写回失败 | 从原对象位置继续核对并重试。元数据发布失败时事务回滚，已用、结果条目和终态保持一致，原对象继续受任务引用保护 |
| 用户取消、任务过期或旧 worker 晚回 | 在账号事务选择 `CANCELLING` 或 `EXPIRING`。按绑定会话执行 Abort 并复查在途分片、会话和唯一键完成事实，必要时重试。对已写出的未发布对象按原版本登记延迟清理。条件写回终态时只释放一次预占，已发布内容保持当前引用 |
| 同内容并发发布、秒传与 GC 竞争 | 用账号锁和同账号 READY 摘要+大小唯一键。复用前必须找到仍拥有完整活动祖先路径的逻辑引用，并锁定对象复查状态及位置。GC 在同一协调规则下检查有效引用与保护任务，再决定是否进入 `DELETING` |

孤儿会话收尾以 24 小时上传任务生命周期确定首版宽限期。从会话发起时间起严格超过 24 小时才可进入中止复核。选定本机 MinIO 实例证明项目后，worker 立即执行首轮，轮次之间等待 1 分钟。每轮最多查询 10 个原对象、读取 5 页会话且每页最多 20 条、处理 10 个候选。每轮和实际中止前均核对实例身份，已绑定会话及仍在创建的任务继续受保护。

对存储会话的清理验证包括在 Abort 前已发出的上传请求。验收同时检查对象版本和仍存在的 Multipart 会话，确保持久终态和残留清理一致。 [S3 AbortMultipartUpload](https://docs.aws.amazon.com/AmazonS3/latest/API/API_AbortMultipartUpload.html)

## 5. 数据库迁移与兼容

- 版本 1 继续使用原文件和 SHA-256。先扩展独立迁移命令和服务启动只读校验，支持有序版本和逐条摘要。命名锁、`dirty`、拒绝未来版本和已有数据保护沿用当前约定。B4 启用时要求版本 2 完整，由独立命令提前迁移，服务启动只核对。失败保留 `dirty` 和现场，已有 B4 业务数据的回退须从已验证备份制定恢复顺序。
- 版本 2 独立新增 `upload_parts`，主键 `(task_id, part_number)`，`task_id` 外键指向已全局唯一的 `upload_tasks.id`。按已批准的 `etag VARCHAR(255)`、`size BIGINT UNSIGNED`、`checksum_algorithm VARCHAR(32)`、`checksum_value VARCHAR(255)`、`observed_at DATETIME(6)` 保存，并保持校验算法和值成对及编号 `1～10000` 的约束。行只来自服务端核对，完成快照和任务状态同一提交。写入和查询从账号已授权任务开始。
- 复用现有 `part_size`、`part_count`、`storage_upload_id`、`expected_sha256` 和租约列。仓储逐步扩展明确的模式分支。现有 SINGLE 的初始化、内容入口、快照、校验、取消、过期和发布回归逐项通过后才开放 Multipart。秒传复用现有 READY 唯一索引及幂等表，在同一事务复查可见引用和配额、确定文件名、创建逻辑条目并保存结果。

## 6. 验收与开发顺序

| 验收场景 | 必须核对 |
|---|---|
| 计划边界 | 0、16 MiB、16 MiB 加 1、恰好整除、末片短、50 GiB 与超限。用合成 1 GiB 以上文件验收实际读写和内存边界，验证临时磁盘不足报错。ListParts 超过一页时可用提供商支持的较小页上限构造真分页，并用夹具验证超过 1000 项的标记递进 |
| 断网、应用及服务重启、URL 过期 | 使用同一任务 ID，源身份复检通过后只补缺失或不匹配的片。回执丢失、源内容变化和重复编号均按协议处理，旧签名拒绝再发起请求 |
| 分片替换和恶意或错误内容 | 同一编号以最新回执核对，旧回执不会提交成功。存储拒绝校验值与正文不符的片，最终对象 SHA-256 错误时不发布且全额释放预占 |
| 完成响应丢失、重复完成、故障时重启 | 从固定会话和唯一键恢复，核对 Get/Head 版本及下载摘要。只有一个发布结果，只结算一次空间。模拟租约过期、数据库提交故障、取消/过期与完成竞争 |
| 同账号复用、权限及物理清理 | 同内容并发发布收敛到一个 READY 物理内容，每条可见逻辑文件独立计费。回收路径或其他账号的内容不能命中。孤儿会话可回收，GC 与新引用竞争无悬空引用 |
| 迁移与 B3 回归 | 同时验证新空库和带 B3 合成数据的版本 1 升级，验证已执行版本摘要、错序和 dirty。原 SINGLE 登录、声明、往返、取消与发布口径均通过 |
