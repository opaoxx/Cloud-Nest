## 第 001 步——读取并校验后端监听地址

完成日期为 2026-11-04，所属阶段为 B0 服务基础。

### 本次目标

启动服务需要一个监听地址，例如 127.0.0.1:18081。本次将地址读取与校验放入 config 包，main 调用它获得结果后启动服务。

方法的输入来自环境变量 CLOUDNEST_HTTP_ADDR，输出为监听地址和 error。变量未设置或为空时使用 127.0.0.1:18081，格式或端口错误时返回原因。

### 文件与调用关系

| 文件 | 职责 |
|---|---|
| internal/server/config/http.go | LoadHTTPAddress 按步骤读取和校验配置 |
| cmd/server/main.go | 获取配置，错误时结束启动，成功时注册路由并监听 |
| internal/server/config/http_test.go | 对正常、错误和边界输入执行验证 |

~~~text
go run ./cmd/server
  → main()
    → config.LoadHTTPAddress()
      → 读取环境变量或采用默认值
      → 拆分 host 和 port
      → 检查数字端口及项目保留端口
      → 返回地址或错误
    → 注册 /ping
    → router.Run(listenAddress)
~~~

### 按注释理解代码

1. os.Getenv 读取环境变量，空值时采用默认值。
2. net.SplitHostPort 拆分地址。比如 127.0.0.1:18081 会得到主机 127.0.0.1 和端口文本 18081，IPv6 使用方括号写法。
3. strconv.ParseUint 把端口文本转换成数字，16 位范围上限为 65535，再排除 0。
4. 检查项目保留的 8080～8090 和 18080，避免误用其他项目的端口。
5. net.JoinHostPort 将主机与数字端口组合为地址，确保 IPv6 方括号及端口格式一致。

当方法返回错误时，main 输出原因并结束启动。配置包负责提供地址，main 负责启动服务。实际端口占用及主机名解析由后续监听操作报告。

### 本次学习概念

结构体可以把相关数据装在一起。DatabaseConfig 中的 Address、DatabaseName、Username、Password 是四个字段，main 拿到一个配置对象，就能把它交给下一步的连接方法，不必传四个分散参数。

## 第 004 步——建立 MySQL 连接池并检查连通性

开始日期为 2026-11-04，所属阶段为 B0 服务基础。

### 编码前的小方案

新增 repository.OpenMySQL(ctx, databaseConfig)，接收 context.Context 和上一轮的 DatabaseConfig，返回 *sql.DB 与 error。复用已有 go-sql-driver/mysql v1.9.2 和标准库 database/sql，本步不新增依赖。GORM 后续装配时复用此连接池。

- 模块边界：repository 管理连接创建、池参数与连通性验证；cmd/server 装配资源、记录日志和启动 HTTP。
- 驱动参数：TCP、ParseTime=true、Loc=time.UTC、utf8mb4、会话 time_zone='+00:00'，拨号/读/写超时均为 5 秒。使用 mysql.NewConnector 和 sql.OpenDB 传递配置，不手工拼接或输出 DSN；不启用迁移专用的 MultiStatements。
- 连接池参数：最大打开连接 10，最大空闲连接 5，连接最长使用 3 分钟。创建连接池后执行 PingContext，整次检查最多 5 秒，也遵守调用方更短的期限或取消信号。
- 失败规则：连接检查失败时关闭新建连接池并返回 nil、带原因的错误；启动入口记录 stage=database 并在 HTTP 监听前结束启动。
- 关闭责任：成功返回的池由启动流程负责。新增 run(logger) 返回错误，池使用 defer 关闭；main 在 run 返回后决定退出码，避免 os.Exit 跳过 run 中的 defer。操作系统信号触发的优雅退出仍按后续独立小步完成。
- 本步 GET /ping 契约不变，不增加业务 SQL、表映射、事务、缓存、消息或跨服务调用；schema_migrations 校验留给下一小步。连接成功只表示启动时检查通过，不代表持续健康。
- 验证策略：本地 TCP 模拟握手不响应验证超时与取消；显式启用真实 MySQL 集成检查，验证池参数、UTC/字符集与关闭；实际启动验证 /ping、错误密码、不可达地址和 HTTP 端口占用后的关闭路径。本步不修改业务数据。
- 提交策略：完成验证后交付，由用户决定 Git 提交。

// 2. 创建连接池，设置连接数量和连接寿命。

### 本次学习概念

连接池 *sql.DB 可以管理并复用多个数据库连接，不需要为每个请求重新登录数据库。本步最多打开 10 个连接，最多保留 5 个空闲连接；最长使用 3 分钟的设置让旧连接定期被替换，不表示每 3 分钟会中断正在执行的查询。

sql.OpenDB 主要创建连接池对象，本身不能证明数据库可用。PingContext 才会实际尝试连接、认证并检查响应，所以日志分别记录“配置读取成功”和“连接检查通过”。这里的 Ping 是数据库驱动检查，与 HTTP 的 /ping 是不同操作。

context.Context 让操作知道何时取消或停止等待。context.WithTimeout 在调用方上下文上再加最多 5 秒的期限；如果调用方只允许 100 毫秒，操作仍应更早结束。驱动的拨号与读写超时提供额外的网络等待限制，后续业务 SQL 仍需要自己的请求上下文。

defer 表示在当前函数返回前执行清理。os.Exit 会直接退出进程，不执行 defer，所以 main 只负责最终退出码，真正的启动流程放进 run。当前保证检查失败及启动流程返回时释放连接；Ctrl+C 等操作系统信号的优雅退出在后续独立步骤实现。

连接器直接接收字段，无需把密码拼成 DSN 字符串；特殊字符由驱动处理。字符集通过专用 mysql.Charset 选项设置，time_zone 通过会话参数设置。实现中遇到过把 charset 放入普通参数导致连接失败的问题，已修复并写入 bugfix_log.md，真实连接测试可防止再次出现。

### 本次学习概念

schema_migrations 是迁移的记录表，可理解为数据库升级记录。version 表示执行了哪次升级；dirty=true 表示迁移可能没有完整执行；checksum 保存当时迁移 SQL 的摘要。

SHA256 会把文件字节转换为固定长度的摘要。本步与迁移命令使用同一算法，比较程序内嵌 SQL 的摘要和已保存摘要，避免程序沿用版本号却悄悄修改已应用的 SQL。它不读取每张业务表的定义，因此不能发现所有手工改表行为。

QueryContext 返回 Rows，Rows.Next 逐条前进，Scan 把数据库列放入变量。遍历结束后还要检查 Rows.Err，因为“读完了”和“读到一半发生网络错误”都会使 Next 返回 false。defer rows.Close 确保遇到版本或摘要错误而提前返回时，也会释放查询资源。

由于当前程序只接受一条版本 1 记录，LIMIT 2 已足够发现多余版本；不能仅使用 WHERE version=1，否则数据库已有版本 2 时可能被忽略。以后增加迁移版本，需要一起扩展迁移命令和本检查规则。

启动检查期间收到信号时，连接或迁移查询会通过同一个 ctx 收到取消通知，已创建的池仍在返回时清理，不再继续启动 HTTP。

### 本次学习概念

goroutine 可以让一个函数在后台独立运行。ListenAndServe 会一直等待请求，放到 goroutine 中后，主流程就能同时等待退出通知，而不会卡在监听调用上。

通道用于传递后台运行结果。这里的 serveErrors 容量为 1，监听结束后可以先放入一个结果，不必等接收方立刻来取。select 同时等待两件事：监听是否失败，以及 ctx.Done 是否收到取消通知。

Shutdown 与 Close 的用途不同：Shutdown 先停止监听，再等正在处理的请求正常结束；Close 会直接断开连接。因而本步先给请求最多 30 秒的完成机会，超过期限才强制关闭，并将这次退出视为失败。

收到信号后，原 ctx 已经取消。关闭时用 context.Background 创建新的期限，才能留出完整的清理时间。也不能仅看到 ListenAndServe 返回 http.ErrServerClosed 就提前结束程序：Shutdown 开始时它便会返回，现有请求可能还没有完成，所以 Serve 会等待 Shutdown 返回。

HTTP 停止之后 Serve 返回，run 中的 defer 才关闭数据库池。这样仍在正常处理的请求可以继续使用数据库；最后 main 返回，操作系统得到正常退出码 0。真正的启动或 HTTP 关闭错误仍记录原因并使用退出码 1。

### 本次学习概念

函数也可以作为参数。main 传入 connectionPool.PingContext 时没有写调用括号，传递的是“以后可以执行这项检查的能力”；HealthService 收到请求后才调用它。这让服务层可以组织规则，而不用亲自创建数据库连接和存储客户端，也方便测试提供可控制的检查函数。

Handler.Ready 是一个创建处理函数的方法。它先保存 checkReadiness，再返回一个 Gin 处理函数；返回的函数会在请求到达时使用保存的检查能力。这种写法让路由层与具体数据库实现分开。

## 第 011 步——增加请求 ID 中间件

开始日期为 2026-11-04，所属阶段为 B0 服务基础。

### 编码前的小方案

新增全局 middleware.RequestID，读取 X-Request-ID。仅接受单个标准 36 字符、带连字符的 UUID v4 且采用 RFC 4122 variant；接受大小写，最终规范为小写。无值、空值、错误格式、其他 UUID 类型、超长、多个同名头或逗号合并值都生成新 UUID v4，不影响原接口状态码或 JSON。

- 复用项目已存在的 github.com/google/uuid v1.6.0，不升级版本。uuid.Parse 会接受一些非标准形式，所以先限定长度为 36，再检查解析结果的 Version 与 Variant，排除无连字符、花括号、URN、零 UUID 等形式。
- 新增 requestcontext.WithRequestID 和 RequestID，使用私有类型键在标准 context.Context 中存取。这个包不依赖 Gin，保留父上下文的取消与期限，供后续服务和日志使用。
- 中间件将有效 ID 同时写入请求上下文、规范化后的请求头及响应头，再调用 Next。下游不需要再次读取无效的原始输入；本步不记录或回显被替换的原始值。
- 路由继续使用 gin.Default，在注册任何路由之前 Use(RequestID())。既有 Logger 与 Recovery 保留；进入 Gin 的正常响应、503、404 和恢复处理的 500 都应带请求 ID。HTTP 协议解析阶段直接拒绝的请求不属于此中间件范围。
- api/openapi.yaml 先增加可选请求头与所有已声明响应的 X-Request-ID 头引用。三个系统接口正文保持原样；后续业务响应与请求日志再接入此 ID。
- 本步不新增数据库表、存储操作、缓存、消息或跨服务契约。不会将 request_id 当作登录身份、幂等键或授权依据。

~~~text

  → RequestID 中间件
    → 读取 Header.Values("X-Request-ID")
    → 单个标准 UUID v4：规范成小写
    → 缺失或无效：生成新 UUID v4
    → 写入标准请求上下文、请求头与响应头
    → Next()
      → 后续中间件
      → 匹配的 Handler → Service
        → 可从 requestcontext.RequestID(ctx) 取得同一 ID
  → 返回原有状态码与正文，响应头附带最终 ID
~~~

### 本次学习概念

中间件是位于处理链中的公共步骤。它可以在具体 Handler 之前准备数据，也可以在 Next 返回后观察处理结果。本步先准备请求 ID，再调用 Next，让后面的接口共用这个标识。

标准 context 既能传递取消与期限，也能携带少量与请求有关的数据。WithRequestID 返回一个子上下文，并通过 Request.WithContext 更新当前请求；后续 Service 再派生超时上下文时，这个 ID 仍可沿调用链读取。

上下文的键使用包内私有类型，而不是普通字符串，避免其他包碰巧也使用 request_id 字符串时覆盖彼此。RequestID(ctx) 把读取细节封装起来：未设置时返回空字符串，调用方不必自己做类型判断。

输入校验不能只依靠 uuid.Parse，因为它还支持 URN、无连字符等形式。本项目先限制为 36 字符，再确认版本和 variant；多个同名请求头也不任选其一，而是生成新值。合法大写输入最终统一成小写，减少后续查找时的差异。

请求 ID 是关联信息，不是登录凭证。客户端可以提交合法 ID，同一个值也可能被用于多次请求；它不能代替账号、会话或幂等键。本步只完成标识传递，结构化请求日志在下一步使用它。

### 本次学习概念

Next 前后的代码执行在两个时刻：之前可记录请求起点，之后才能知道处理用了多久、最后返回什么状态。只在 Next 前记录状态，可能把后面产生的错误误记为默认 200。

中间件顺序也影响结果。Recovery 必须在 RequestLog 的内层，才能先把异常变成 500，再让日志方法观察到最终状态。否则 panic 会使日志方法在 Next 后的代码没有机会执行。

JSON 日志把字段分开放置，便于按 request_id 查找和按 status 筛选。duration_ms 是毫秒数字，便于比较性能；日志级别由最终 HTTP 状态决定。这里不把 c.Errors 或 panic 内容直接拼入日志，因为它们可能包含请求数据。

### 本次学习概念

DTO 在这里是 HTTP 层传输的数据结构。ErrorResponse 这个 Go 结构体对应最外层的 error 和 request_id，ErrorDetail 对应内部的 code、message 和 details。把它们定义在独立文件，可以在后续错误处理里复用，而不用每个 Handler 临时拼一套字段。

HTTP 404 表示请求没有匹配到接口，ROUTE_NOT_FOUND 是本项目进一步说明原因的稳定错误码。它和未来的 ENTRY_NOT_FOUND 不同：前者是接口没匹配，后者是接口存在但业务资源没有找到。

## 第 014 步——统一可恢复异常的 500 响应

开始日期为 2026-11-05，所属阶段为 B0 服务基础。

### 编码前的小方案

新增 handler.InternalError 作为 Recovery 回调，复用 ErrorResponse/ErrorDetail。普通 panic 被恢复且响应尚未提交时，返回 HTTP 500、application/json、Cache-Control: no-store，正文为 error.code=INTERNAL_ERROR、message=服务内部错误，请稍后重试、details=null，并附当前 request_id。不返回原始 panic 或堆栈。

- 已经写出状态或正文时，HTTP 不能回滚；回调仅 Abort，不覆盖状态、正文或已有头，也不追加 JSON。未写出但已有待发送的 Content-Length/Content-Encoding 时先清除，明确设置 JSON Content-Type，防止长度、编码或类型与新正文冲突。
- 新增 middleware.Recovery(handleRecovery)，沿用 Gin 自带恢复和断连判断，但关闭转储；普通异常交给回调前只在 Gin 请求上下文写入私有布尔标记，不保存原始异常。
- RequestLog 识别该标记：对已恢复异常使用 ERROR，增加 recovered_panic=true，但 status 仍记录实际响应状态。非异常日志字段和分级保持原样。该标记让“已提交 200 后才 panic”仍能被日志识别，此前的 INFO 复现已先写入 bugfix_log.md。
- Router 的链仍为 RequestID → RequestLog → Recovery → Handler，Recovery 回调由 router 绑定 handler.InternalError。原有 404、三个系统接口成功响应及 ready 的 503 不变。
- OpenAPI 先增加 components.responses.InternalError 并在三个 GET 操作下引用 500；限定为未提交响应的普通恢复场景，不新增测试路由。网络断连等特殊情况沿用 Gin 已有处理逻辑。
- 本步不增加依赖、业务表、存储操作、缓存、消息或跨服务调用。测试覆盖不同 panic 载荷、ID 一致与隐私、未提交头修正、已提交响应保护、并发，以及真实 HTTP 与异常后继续服务能力；Git 提交由用户决定。

| 文件 | 本次职责 |
|---|---|
| internal/server/http/handler/internal_error.go | 判断响应是否已提交，未提交时返回统一错误 JSON |
| internal/server/http/middleware/recovery.go | 关闭原始转储，标记普通异常并调用响应回调 |
| internal/server/http/middleware/request_log.go | 识别异常标记，记录 ERROR 和实际状态 |

    → 未提交：读取 request_id，清理冲突的待发送头
      → 返回 INTERNAL_ERROR 的 500 JSON
  → 外层 RequestLog
    → ERROR + recovered_panic=true + 实际 HTTP 状态
~~~

### 本次学习概念

Recovery 的回调是“异常被捕获后如何响应”的处理方法。本步继续复用 Gin 的恢复能力，只把响应处理换成本项目的 InternalError。回调签名中的 `_ any` 表示原始异常参数不会被使用，因此不会把内部错误字符串直接发给客户端。

响应已提交与仅设置状态不同。Status(201) 可以先暂存一个状态，尚未写出时仍能改成 500；WriteHeaderNow、正文写入或 Flush 之后，状态和头已经发送，就不能再回滚。Writer.Written 用来区分这两个阶段。

因此已提交的响应可能仍是 200，却确实发生了异常。日志不能伪造为 500，也不能把它当作普通成功；本步保留真实 status，再用 ERROR 与布尔 recovered_panic 标记表达异常。这个标记只属于当前 Gin 请求，不传给其他请求，也不保存原始载荷。

未提交时，原 Handler 可能已经设置了文件长度、gzip 编码或下载类型。错误响应改为 JSON 后，需要清理长度和编码，并明确类型，否则客户端可能按旧的响应头错误解析新正文。

统一 500 使用上一轮的 ErrorResponse 和 ErrorDetail，不需要重新定义结构。它与 404 的错误码和提示不同，但 details=null、request_id、响应头和日志的关联规则一致。

- 协议和域名转为小写，IPv6 使用压缩标准表示；显式端口为 1～65535，去掉前导零及 HTTP 80/HTTPS 443 默认端口。保留其他端口以及来源之间的协议/主机差别。按规范化值去重，保留首次出现的顺序。
- 配置解析使用单独的辅助方法，不复用存储地址解析器：Origin 要求显式协议，并有域名与默认端口语义。错误只含环境变量名、条目位置与规则，不回显可能误填的凭证。

## 第 016 步——接入 CORS 来源检查与预检处理

开始日期为 2026-11-05，所属阶段为 B0 服务基础。

### 编码前的小方案

本轮只接入 CORS，不实现登录、文件接口或前端联调。输入是第 015 步已经规范化的来源列表以及请求头；输出是继续处理、预检 204 或统一 403。main 显式把 allowedOrigins 传给 NewRouter，路由装配 RequestID → RequestLog → Recovery → CORS → Handler。

- 无 Origin 的工具或原生客户端请求继续原流程；有 Origin 时只接受单个与白名单完全相等的来源。空值、null、通配符、重复头或非规范化值不放行，不按域名后缀匹配，也不将请求来源再次规范化。
- 允许来源返回明确的 Access-Control-Allow-Origin 和 Allow-Credentials: true，普通响应暴露 X-Request-ID。未知来源及非法预检返回 403，错误码 CORS_FORBIDDEN，details=null，不附带跨域放行头，不回显输入；浏览器脚本通常只能看到 CORS 错误，可在开发者工具核对状态和 ID。
- OPTIONS 且存在 Access-Control-Request-Method 才按预检处理。支持 GET、HEAD、POST、PUT、PATCH、DELETE、OPTIONS；请求头只允许 Authorization、Content-Type、Idempotency-Key、X-CloudNest-Client、X-Request-ID，不区分头名称大小写。方法必须单个且大小写准确，列出的请求头不能含空项或未知项；通过返回 204、固定允许列表和 no-store，不执行 Handler 或依赖检查。不增加预检缓存时长。
- 对所有响应合并 Vary: Origin；OPTIONS 再合并 Access-Control-Request-Method、Access-Control-Request-Headers，不覆盖已有 Vary。预检仅表示跨域策略许可，不表示方法或路径已实现；不带预检方法头的普通 OPTIONS 仍按现有路由匹配。
- 为让尾斜杠请求也经过中间件，关闭 Gin 在执行中间件前发生的尾斜杠自动重定向；例如 /ping/ 现在经过来源检查后返回统一 404，不再自动跳转。保持固定路径重定向关闭。
- 沿用统一错误 DTO，跨域拒绝处理函数由路由注入中间件，避免 middleware 依赖具体 Handler。保留既有请求 ID、日志和异常恢复；不新增第三方依赖，不修改数据库或容器，不提交 Git。
- 测试覆盖放行、拒绝、预检方法/请求头边界、无 Origin、404/500/503、缓存头合并、真实 TCP 与混合并发请求。实现和验证后补充实际结果。

### 本次学习概念

前端 http://127.0.0.1:5173 和后端 http://127.0.0.1:18081 的端口不同，属于不同来源。CORS 是后端通过响应头告诉浏览器“这个页面可以读取响应”。它不检查用户是谁，也不能替代后续的登录与权限判断。没有 Origin 的命令行请求继续通行，未来仍需携带业务接口要求的认证信息。

发送 JSON 或自定义请求头时，浏览器可能先发送一次 OPTIONS。比如准备 POST 登录，会先声明 Access-Control-Request-Method: POST，并通过 Access-Control-Request-Headers 列出准备发送的头名称。服务器许可后，浏览器才发实际请求。本轮 204 表示预检许可，即使登录接口尚未实现，也不能据此判断登录已可用。

allow_credentials=true 为后续 Cookie 请求准备协议许可；它不会创建 Cookie，也不会使页面自动携带凭证。Allow-Origin 使用匹配的明确来源，不返回通配符。普通允许响应额外暴露 X-Request-ID，因为自定义响应头需要通过 Expose-Headers 才能由跨域页面脚本读取。[CORS 响应头说明](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS)

Vary 告诉缓存“来源不同的请求，不能直接复用同一份响应头”。因此无 Origin 的响应也需要 Vary: Origin；OPTIONS 还按预检方法和请求头区分。合并时保留已有 Accept-Encoding 等值，不覆盖其他中间件的缓存条件。

白名单在构造中间件时复制成 map，此后只读，用于并发请求查找。修改调用方原切片不会改变运行中的规则；修改环境变量也不会热更新，需重启后端。

## 第 017 步——封装有大小上限的 JSON 请求读取

开始日期为 2026-11-05，所属阶段为 B0 服务基础。

### 编码前的小方案

新增 HTTP binding.ReadJSON(ctx, &requestDTO) bool。输入为 Gin 请求上下文和非 nil 请求结构体指针；成功填入 DTO 并返回 true，输入失败则使用现有 ErrorResponse 返回错误并 Abort，调用方立即 return。调用关系为 Handler → ReadJSON → 后续参数校验/业务逻辑，错误沿用请求 ID、完成日志和 CORS。

- 只支持单个 application/json Content-Type，允许参数与大小写规范化，charset 仅支持 UTF-8；缺失、重复、格式无效或其他媒体类型返回 415 UNSUPPORTED_MEDIA_TYPE。Content-Encoding 仅允许缺失或单个 identity，不自动解压。
- 通过 http.MaxBytesReader 限制实际读取量，最多接收 1 MiB（1048576 字节），检测时最多再读一个字节。先受限读取完整正文，再解析；实际超限优先返回 413 REQUEST_BODY_TOO_LARGE，包含尾随空白的所有正文字节都计入，不仅依靠可缺失或不可信的 Content-Length。读取失败返回固定 400 INVALID_ARGUMENT，不回显底层错误。
- 正文必须是有效 UTF-8 字节且顶层为单个 JSON 对象，空正文、null、数组、语法错误、类型错误、未知字段、第二个 JSON 或尾随非空白内容返回 400 INVALID_ARGUMENT。允许对象前后的 JSON 空白；结构体字段匹配及重复键等行为沿用 Go encoding/json，不另造 JSON 解析器。
- 使用 json.Decoder.DisallowUnknownFields；正文只解析为请求 DTO。必填、字符串长度、null 字段和业务规则在下一步校验。false 时 DTO 可能已有部分字段，禁止继续使用；调用方传入无效目标是程序错误，由已有 Recovery 返回统一 500，不伪装成客户端 400。
- 所有新输入错误均使用 error 与 request_id、details=null、Cache-Control: no-store，提示为固定公开文本，不记录原始正文、未知字段名或解码错误。

### 本次学习概念

`&input` 是把变量的地址交给读取方法，这样方法可以将解析结果填回 input。`any` 让同一个方法可以接收不同请求结构体的指针；字段名称由结构体上的 json 标签决定，所以将来登录、创建目录等接口可以共用读取过程，同时各自定义 DTO。

Handler 的基本写法如下；这是后续接口使用方式的示例，本轮没有注册这个生产端点：

~~~go
// 1. 读取单个 JSON 对象，输入失败后立即结束当前处理函数。
var input SomeRequestDTO
if !binding.ReadJSON(requestContext, &input) {
    return
}

// 2. 检查字段必填、长度及业务规则，再调用 Service。
// 下一步按具体接口补充。
~~~

ReadJSON 内部会 Abort，但 Abort 只停止 Gin 后续的处理函数，不会代替当前函数中的 return。解析错误时 DTO 可能已经填入部分字段，所以必须在 false 分支立即返回，不能继续调用业务方法。

“语法能解析”与“业务参数正确”是两层检查。`{}` 是合法 JSON，但不保证用户名和密码已填写；字符串字段接收到 null 时也可能保持零值。下一步使用具体 DTO 的校验规则判断必填与长度，本轮不提前混入登录规则。

1 MiB 是 1048576 字节，不是字符数；中文通常占多个 UTF-8 字节。限制包含字段名、引号、分隔符和尾随空白。MaxBytesReader 按实际读取量限制，io.ReadAll 只读取这段有上限的正文；检测超限时最多额外读取一个字节。Content-Length 不能覆盖未知长度的分块请求，因此不能只拿它与上限比较。[Go 请求体限制](https://pkg.go.dev/net/http#MaxBytesReader)

只调用一次 Decode 可能漏掉正文后面的第二段 JSON。第二次 Decode 必须返回 io.EOF，表示剩余内容只有 JSON 空白且已经结束；解出了第二个值，或遇到垃圾内容，都应拒绝。

HTTP 状态与固定错误码分别为：

| HTTP | 错误码 | 含义 |
|---|---|---|
| 400 | INVALID_ARGUMENT | 空正文、JSON 结构/字段/类型错误、读取失败等 |
| 413 | REQUEST_BODY_TOO_LARGE | 实际正文超过 1 MiB |
| 415 | UNSUPPORTED_MEDIA_TYPE | 非支持的 Content-Type、字符集或压缩编码 |

这些错误均返回 details=null、当前 request_id 和 no-store。原始解码错误可能带入未知字段名或输入信息，因此响应只返回本地固定提示，日志沿用原有元数据，不添加正文。

### 本次学习概念

DTO 是接口接收的数据结构。LoginRequest 回答的是“客户端登录时要提交哪些字段”，因此既有账号信息，也有设备信息。它不等同于数据库的一张表：username 对应 users.username，device_name 将来映射到 user_devices.name；password 只用于密码比对，不能明文存入数据库；client_type 用来选择 Web Cookie 或原生凭证交付方式。

Validate 使用值接收者，检查的是一份请求副本；方法不修改字段，不访问数据库。返回 nil 表示这六个字段的格式合格，返回 FieldError 则说明第一个不合格字段。它不能证明账号存在，也不能证明提交的密码正确。按固定顺序短路返回，让前端和测试得到稳定结果。

字段错误包含两部分：Field 是可公开的 JSON 字段名，Message 是固定规则提示。InvalidArgument 把它们放到统一响应中，例如缺少用户名时：

~~~json
{
  "error": {
    "code": "INVALID_ARGUMENT",
    "message": "用户名须为 1～64 个小写字母、数字或下划线",
    "details": {"field": "username"}
  },
  "request_id": "28ee758a-0727-42de-ae7d-3bb33155e148"
}
~~~

这与上一步解析错误的 details=null 有区别：字段校验已经知道是哪个已定义字段不符合规则，前端可以定位输入框；解析错误可能是正文结构、字段类型或未知字段问题，本轮仍沿用固定提示，不回显原始解析错误。

密码按字节计数，因为现有 bcrypt 的密码输入上限是 72 字节；24 个“中”占 72 个 UTF-8 字节，可以通过长度检查，25 个则超限。设备名称按 Unicode 码点计数，与 VARCHAR(100) 的字符容量对应；一个 emoji 可能由多个码点组合显示，因此这里并非按屏幕上看到的图形个数计数。[bcrypt 密码上限](https://pkg.go.dev/golang.org/x/crypto/bcrypt#GenerateFromPassword)

安装 ID 和请求 ID 各有用途。X-Request-ID 关联一次请求的响应与日志；installation_id 由客户端生成一次并持久保存，使多次登录可以识别同一客户端安装。安装 ID 格式正确不等于设备已经授权。当前采用标准小写 UUID v4，避免 ascii_bin 数据库中同一个 UUID 因大小写不同而被当成不同安装。

平台与凭证交付方式也需要区分：浏览器是 WEB/web，Windows 桌面端是 WINDOWS/native，Android 客户端是 ANDROID/native。字段由客户端自报，未来 Handler 仍必须检查浏览器 Origin 和 X-CloudNest-Client；不能因为正文声称 native 就跳过 Web 规则。

### 本次学习概念

连接池负责管理实际数据库连接，GORM 负责组织 SQL、绑定参数和把查询结果填入结构体，Repository 则把这些数据库细节封装为“按用户名查登录账号”这个方法。以后 Service 只调用方法，不需要知道表名、列名或 GORM 的写法。本轮使用已有池，避免又建立一套连接数量和关闭规则。[复用连接池](https://gorm.io/docs/connecting_to_the_database.html#Existing-database-connection)

数据库投影指的是“只取这次需要的列”。users 表还有配额、展示名称和时间等字段，但密码验证只需要用户 ID、密码摘要和状态，所以本次显式查询三列。models.LoginAccount 是三列的只读映射；domain.LoginAccount 是提供给业务层的内部对象。两者虽然当前字段相同，职责不同：前者知道 GORM 列映射，后者不依赖数据库工具，也不是 HTTP DTO。未来完整用户模型和对外响应随对应功能再增加。

查询的核心是：

~~~go
store.database.WithContext(queryContext).
    Select("id", "password_hash", "status").
    Where("username = ?", username).
    Take(&record)
~~~

`?` 是参数占位符，username 作为值单独绑定。即使输入含引号或 SQL 片段，也不能因此改变查询条件。空字符串仍是明确的 username 条件，不会自动变成“随便查一个用户”。正式登录仍须先经过第 018 步校验，这里的参数绑定是数据访问边界自身的保障。

Take 表示只取一条记录，没有记录时 GORM 会给出 ErrRecordNotFound；本方法将它换为 domain.ErrAccountNotFound，业务层通过 errors.Is 判断即可，不需要依赖 GORM。网络故障、池已关闭或字段读取失败属于另一类错误，不能转换成账号不存在。真正返回登录结果时，还应把“账号不存在”和“密码错误”统一成凭证失败，避免泄露账号存在性；这不是本轮查询方法的职责。[GORM 单行查询](https://gorm.io/docs/query.html)

查询保留调用方的 context，再增加最多 5 秒的限制。调用方只给 50 毫秒时不会被延长成 5 秒；已经取消时也不会继续查询。`defer cancel()` 用来释放这次查询的计时资源，不会关闭共享数据库连接池。

DISABLED 账号仍会被查出来，因为“记录是否存在”与“是否允许登录”是两个判断。Repository 返回事实，后续 Service 再执行账号状态和密码规则。密码摘要只供内部比对，字段上的 json:"-" 防止它意外进入 JSON；这不能代替编码约定，仍禁止把整个账号对象写入日志或作为响应。

本轮两个直接依赖是 GORM 和 MySQL 方言，新增的 inflection、now 是它们需要的间接模块。go mod tidy 也记录了 GORM 自身测试使用的 SQLite 模块校验值，但本项目代码没有引入 SQLite 或创建 SQLite 数据库，底层 MySQL 驱动版本保持不变。

## 第 020 步——使用 bcrypt 比对原始密码

### 编码前的小方案

新增 service.VerifyPassword(passwordHash, rawPassword) (bool, error)，复用现有 golang.org/x/crypto v0.57.0，不新增依赖。它只负责密码比对，不查询账号、判断状态、创建会话或签发令牌；通过测试与第 019 步只读查询衔接，不注册生产登录端点。

- 匹配返回 true/nil；不匹配返回 false/nil；摘要合法时，空密码、超过 72 字节或非 UTF-8 候选也返回 false/nil，避免未经过 DTO 的调用放宽第 018 步输入范围。所有候选密码均保持原文，不 trim、不归一化、不重新生成摘要后做字符串相等比较。
- 摘要先检查本项目支持的标准 60 字符 $2a$/$2b$/$2y$ 外形，再由 bcrypt.Cost 解析成本。接受成本 4～14，覆盖当前种子账号的 12；超出支持范围或格式异常返回 domain.ErrInvalidPasswordHash。成本上限是本项目当前策略，不是 bcrypt 库的最大值；以后提高成本需一起调整与验证，不能自动接受库允许的极高成本。
- 调用 bcrypt.CompareHashAndPassword；只有 nil 才表示匹配，ErrMismatchedHashAndPassword 映射为 false/nil，其他错误映射为固定 ErrInvalidPasswordHash。错误不包装原始摘要、密码或解析器信息，不记录日志；摘要异常属于内部数据问题，未来不会直接作为普通凭证错误暴露给浏览器。
- 只能识别结构上异常的摘要；若摘要被改成另一段外形合法的内容，无法仅凭错误密码区分它与真正不匹配。这里不承诺检测所有数据库内容损坏。
- 方法同步执行，bcrypt API 不接受 context，本轮不通过后台 goroutine 制造可取消的假象；后续登录编排再检查上下文、实施失败限流和并发控制。本轮的成本上限约束单次工作量，但不是时间超时承诺。
- 验证正确/错误、密码空格/大小写/Unicode/72 字节边界、随机盐、格式/成本边界及固定错误信息；另以 CLOUDNEST_PASSWORD_TEST=1 只读查询已有 root 并验证开发密码，不打印摘要、不改动账号。测试用临时摘要使用最低成本 4 缩短等待，真实种子成本 12 保持不变。不提交 Git。

### 本次学习概念

数据库保存的是密码摘要，不是明文。登录验证不会把摘要解密回密码，也不会比较“原始密码是否等于摘要字符串”。CompareHashAndPassword 会使用已有摘要携带的盐和成本，对候选密码完成验证。我们只调用现成库，不实现密码算法。[bcrypt API](https://pkg.go.dev/golang.org/x/crypto@v0.57.0/bcrypt#CompareHashAndPassword)

盐是生成摘要时使用的随机信息。同一个密码生成两次摘要，结果通常不同；因此重新 GenerateFromPassword 后与数据库字符串比较不是正确验证方式。测试专门生成两个不同摘要，并确认原密码可以分别通过验证。

成本参数控制 bcrypt 的计算工作量，不是密码长度，也不是固定耗时秒数。现有初始化账号使用 12；本方法目前接受 4～14。4 用于快速生成临时测试摘要，不修改真实账号的 12；未来若提高生产成本，需要一起评估本方法上限。库允许的更高成本不代表本项目应直接执行，本轮会在比对前拒绝超出策略的摘要。

bool 和 error 分开表达两个维度。matched 回答“密码是否匹配”，error 回答“验证过程能否按预期执行”。调用方应先看 error，再使用 matched：数据库摘要异常与普通密码错误需要不同的内部处理。错误本身是固定文本，既不附带原始密码，也不附带摘要或库解析器信息。

密码每个字节都保持原样：“root”和“ root ”是不同候选，“ROOT”也与“root”不同。Unicode 字符不进行归一化，因此视觉上相似但编码不同的候选仍可能不匹配。保持原文才能和账号最初设置的密码一致。

本轮仍没有完成登录。一个 ACTIVE 账号的密码匹配后，还需要设备、会话和令牌等流程；DISABLED 账号即使密码正确，也不能据此判定允许登录。下一步先把查询、比对与状态检查组织成服务，再逐项补充后面的流程。

### 本次学习概念

`store.FindLoginAccountByUsername` 后面没有括号时，是把查询能力交给服务；不是在构造服务时立即执行查询。服务把它保存到 findAccount 字段，收到实际 Authenticate 调用后才传入上下文和用户名。这种做法让业务规则不必知道 GORM 或 MySQL，测试也能换成简单函数来观察执行顺序。

现在有三种各司其职的数据：

| 类型 | 保存什么 | 用在哪里 |
|---|---|---|
| dto.LoginRequest | 客户端提交的用户名、原始密码及设备信息 | HTTP 请求读取和格式校验 |
| domain.LoginAccount | 数据库已有的 ID、密码摘要和状态 | 服务内部进行凭证判断 |
| domain.VerifiedAccount | 检查通过后的用户 ID | 后续设备和会话步骤的输入 |

服务不直接返回查询得到的 LoginAccount，这样调用方不会顺手拿到密码摘要。VerifiedAccount 只证明本次凭证和状态检查通过，还不是登录会话或访问令牌；后续写入会话时也需要在相应事务内重新核对状态，不能把此只读快照当作永久授权。

先比对密码，再判断禁用状态，是为了避免错误密码得到一个能确认账号状态的结果。不存在账号与密码错误都返回同一个 ErrInvalidCredentials，文本固定；知道正确密码后，才可能得到 ErrAccountDisabled。数据库故障或摘要异常是内部处理问题，应交给后续 HTTP 错误映射，不能一律称为用户名或密码错误。

仅统一提示还不等于统一运行路径。如果不存在账号就立即返回，而存在账号必须完成 bcrypt，调用耗时可能有明显差别。因此未命中时也使用固定、非账号的测试摘要做一次计算，而且无论是否匹配都返回凭证错误。该摘要在开发时生成一次，不在每次请求中重复生成，也不代表任何账号。不同真实账号成本或数据库延迟仍可能造成差异，本轮不承诺恒定耗时。[认证错误处理说明](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html#authentication-and-error-messages)

context 取消是通知，不会自动中断所有函数。查询沿用它自己的可取消行为，bcrypt 仍同步执行；服务在计算前后检查状态，确保计算过程中收到取消时，结束后不会继续返回身份。测试替换私有比对函数，模拟在该阶段取消，验证的是边界处理，不是假称已经中断真实 bcrypt 计算。

### 编码前的小方案

新增 HTTP security.LoginSourcePolicy，通过 NewLoginSourcePolicy(allowedOrigins) 复制第 015 步白名单。Allows(request, clientType) 返回 bool，不依赖 Gin、不读取或修改 JSON、不查询凭证；由 Handler 在 ReadJSON → DTO.Validate 后调用，失败交给 handler.ClientSourceForbidden，成功才可调用 CredentialService。

| 模式 | JSON client_type | X-CloudNest-Client | Origin |
|---|---|---|---|
| Web | web | 必须为单个 web | 必须单个且与白名单完整来源严格一致 |
| 原生 | native | 必须为单个 native | 必须不携带，显式空值/null 也拒绝 |

- 两种模式都显式要求客户端声明头，不默认选择模式；客户端头与正文必须完全一致，不自动去空白或转大小写。重复、合并列表、空值、未知类型均拒绝。platform 与 client_type 的组合继续由 DTO 校验。
- Web 的 Origin 不二次规范化，不做前缀/后缀匹配，拒绝空值/null/通配/重复或非白名单来源。原生只要带 Origin 就拒绝，包含白名单来源也不能例外；不根据 User-Agent、Cookie 或 Referer 猜测客户端类型，不做 Referer 回退。
- 独立校验器在没有 CORS 中间件时也能按白名单判断。生产路由仍先执行既有全局 CORS：未知 Origin 可先得到 CORS_FORBIDDEN；允许来源但登录声明不合规则返回新的 CLIENT_SOURCE_FORBIDDEN。两者都不会进入凭证查询，合法预检继续由 CORS 返回 204，不检查尚未发送的正文和实际客户端头值。
- 新 403 沿用 ErrorResponse，固定 message、details=null、当前 request_id 和 no-store，不输出原始头、密码或正文。被 CORS 放行的 Web 页面可以读取此业务前置拒绝响应；没有 Origin 的原生请求不增加 CORS 放行头。
- 客户端标记只用于约束请求来源与后续凭证交付模式，不证明调用者确实是某个原生程序，也不代替密码认证。原生软件若使用会自动附带 Origin 的 WebView/浏览器网络层，不能直接按 native 规则调用；应使用匹配部署方案的请求方式。
- 本轮不新增生产登录端点、不修改现有 GET、不接会话/令牌或数据库。通过纯策略测试和生产路由上的测试专用 POST 验证完整 JSON/DTO/来源/凭证调用顺序、403 与预检、真实 TCP、并发及切片复制；更新共享 OpenAPI 来源头和 403 契约，不给现有 GET 添加登录专用规则。不新增依赖、不提交 Git。

### 本次学习概念

CORS 和登录来源策略检查的内容不同。CORS 根据来源和预检规则决定是否放行跨域响应，但没有 JSON 正文里的 client_type，也不会替登录接口要求客户端标记。登录来源策略是在解析出请求 DTO 后，进一步检查来源、正文模式和自定义头是否一致。因此通过了 CORS 的请求，仍可能因为登录来源规则不合格返回 403。

两层使用同一份启动配置复制出的白名单。来源比较以完整字符串为单位，不把 localhost 与 127.0.0.1 混用，也不把后缀相似的域名当成同一个来源。修改配置后需要重启，原切片修改不会影响既有策略。

Origin 通常由浏览器网络栈提供，表示发起请求页面的协议、主机和端口；它可能为 null。本项目 Web 登录要求明确白名单来源，因此 null、缺失或显式空值都不能通过。前端不需要也不应把 Origin 当普通自定义头手工填写，而是在正确页面来源下发出请求。[Origin 说明](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Origin)

X-CloudNest-Client 是本项目自己的声明头，需要客户端显式发送。Web 用 web，原生用 native，且必须与正文一致。这个头不证明用户身份，也不证明调用者确实是官方客户端；账号仍需要密码验证。原生请求若带 Origin，即使来源在白名单内，也不能仅凭正文声称 native 就进入原生模式。

策略不根据 Referer、Cookie 或 User-Agent 自动补出模式。尤其是 Windows 桌面壳内的 WebView 请求，可能仍由浏览器网络栈发出；将来 Wails 原生模式应通过合适的原生 HTTP 通道调用。Flutter Android 原生 HTTP 调用按 native 规则传头。具体客户端接入时再验证实际发送的请求，而不是只看应用运行在哪里。

预检中的 Access-Control-Request-Headers 只列出将要使用的头名称，尚无实际 JSON 正文和 X-CloudNest-Client 值。所以本轮不拿登录来源策略检查 OPTIONS 预检；先由 CORS 审核允许列表，再对真实 POST 执行全部规则。

### 编码前的小方案

新增 service.LoginFailureLimiter，不依赖 HTTP、数据库、Redis 或后台任务。NewLoginFailureLimiter 创建空记录；Begin(sourceIP netip.Addr, username string) 同时检查 IP 和用户名的额度，返回完成回调、建议等待时长、error。只有拿到回调才可执行后续凭证查询，结束时必须结算。

- 每个维度采用首次预留起 60 秒的固定窗口，最多 10 次失败。为防止并发请求同时通过“先查计数”的空隙，准入同时占用在途名额，failures+inFlight 不得超过 10。IP 与用户名分别累计，不只统计某个 IP/用户名组合。
- 完成回调 complete(true) 将预留转成一次错误凭证失败；complete(false) 只释放预留，不清除已有失败。调用方只对 errors.Is(err, domain.ErrInvalidCredentials) 使用 true，成功、取消、内部故障及正确密码的禁用结果不增加失败次数。先 defer complete(false)，再在已知结果后显式结算，避免提前返回泄漏名额。
- 用 sync.Mutex 使双维度检查与预留原子完成，锁在 Begin 返回前释放；凭证查询和 bcrypt 在锁外运行。回调用 sync.Once 保证第一次结算生效，多次或并发重复调用不重复计数。
- 窗口过期时清除失败数；没有在途请求的过期记录删除，有在途请求则保留预留并按当次操作时间开启新窗口。跨窗口的请求结束时在结束所在窗口结算，不允许清理删掉仍被回调引用的记录。已拒绝请求不增加次数，也不把尚未到期的窗口不断续期。
- 最多 4096 条记录，IP 与用户名各占一条；同时预留两条，容量不足时不部分插入、不驱逐未过期记录以绕过限制，直接受限。建议等待值采用相关阻塞窗口的剩余时间；容量受限时参考最早窗口，等待不是一定放行的承诺（尤其还有在途请求时）。无失败且无在途的空记录在结算时立即释放。
- 输入验证保证 key 大小有界：IP 必须有效且无 zone，IPv4 映射 IPv6 用 Unmap 合并；用户名严格为 1～64 个小写 ASCII 字母、数字或下划线。无效输入返回固定错误，不包含原始值。可信来源 IP 的提取与代理策略在下一步 HTTP 接入时实现，本轮不读取转发头。
- 计数仅在本进程内，重启清空，不适用于多实例共享限制；固定窗口存在边界突发的特性，不宣称任意滚动 60 秒最多 10 次。若调用方不结算，在途记录会继续占用额度但不会突破总记录上限；实际接入必须使用 defer。
- 使用可替换的私有时间来源做确定性测试，不通过 sleep 等待一分钟；验证 10 次边界、双维度、成功/错误分类、窗口与在途、幂等、容量、输入规范及并发。通过测试与 CredentialService 衔接，不添加生产端点或 HTTP 429，不变更数据库、容器或依赖，不提交 Git。

### 本次学习概念

只记录“某个 IP＋某个用户名”的配对不够。攻击者可以在同一 IP 下不断换用户名，也可以用不同 IP 尝试同一账号。因此 records 中分别保存两类 key：scope=ip 以及 scope=username；一次尝试必须同时取得两边的名额。

失败计数在请求结束后才知道，但准入判断发生在请求开始时。如果只是先看 count 再做登录，64 个并发请求可能同时看到“还没到 10 次”。inFlight 是预留名额，用来把还没得出结果的请求也纳入额度。本实现要求 failures+inFlight 最多为 10；错误凭证把预留变成失败，其他结果只释放预留。它是失败限流及在途约束，不是所有成功请求每分钟最多 10 次。

mutex 让“检查两个维度、检查容量、同时预留”成为一个不能被其他请求插入的操作。凭证查询和 bcrypt 在 Begin 返回后才执行，此时锁已释放，不会因为一个慢密码计算而一直占住全局锁。[Go 同步工具](https://pkg.go.dev/sync)

Begin 返回的 complete 是一个函数。它记住了本次预留的两条计数记录，稍后请求结束时再执行，因此称为完成回调。sync.Once 保证这个回调只结算第一次：主动结算后，defer 再调用也不会重复增加失败或把在途数减成负数。调用者无需自己保存或修改 map。

窗口从该记录首次预留开始计算 60 秒；它不是滚动时间段算法。到期时旧失败清零，已经在执行的请求仍占用预留，结束时计入当前窗口。清理不能直接删掉这些记录，否则旧回调会对失效对象结算，使新请求绕过限制。被拒绝的请求不会不断把到期时间往后推。

有界不仅要求最多 4096 条记录，也要求单个 key 的长度有限。本轮只接受规范的用户名和解析后的 IP；IPv4 映射 IPv6 会合并为同一个 IPv4 计数，避免同一地址的不同表示分裂额度。记录满时拒绝新键，不能随意删掉已有失败来腾位，否则限制会被不断换键绕过。

建议等待时长只告诉调用方稍后重试。若 IP 和用户名都达到额度，要等较晚的阻塞窗口；容量满时参考最早可能释放的窗口。仍有在途请求未结束时，到期不保证一定有名额。这个 duration 到 HTTP Retry-After 的整数秒转换留到下一步。

### 本次学习概念

RemoteAddr 是服务器记录的连接对端地址，通常形如 192.0.2.1:1234 或 [2001:db8::1]:1234；请求头中的 X-Forwarded-For 等值则可能由调用者自行填写。当前直连开发模式只根据前者计数，变更转发头不能改变限流 IP。端口用于确认地址格式，最终计数只使用 IP；IPv4 映射 IPv6 统一为 IPv4。[Go HTTP 请求说明](https://pkg.go.dev/net/http#Request)

若将来部署反向代理，后端看到的连接对端可能是代理。本轮不会据此自动信任转发头，必须明确可信代理后再调整规则。Vite 开发代理下，多个 Web 请求可能共用本机代理 IP，这是当前保守直连策略的结果，不应靠随意放开请求头来解决。

LoginAttemptGate 是 HTTP 与已有业务能力之间的适配器：HTTP 负责提供连接地址，限流器负责名额和窗口，CredentialService 负责凭证判断。Gate 本身不写 HTTP，所以可以独立测试取消、异常和结果，也不在里面混入会话或令牌逻辑。每个请求共用同一个 limiter；不能在每次请求中重新创建限流器，否则历史次数会丢失。

上一小步要求调用方记住完成回调，本轮把这个细节包进 Gate。获得名额后先登记 defer complete(false)，再调用凭证服务；如果抛出 panic，调用栈退出时也会释放预留。正常情况下只有 ErrInvalidCredentials 使用 true，成功、取消和其他内部错误都不增加失败次数。预留覆盖本次凭证检查阶段，之后设备/会话事务随对应功能实施。

Retry-After 采用等待秒数形式。若还剩 1.2 秒，返回 1 会让客户端可能提前重试，因此本轮返回 2；即使只剩 1 纳秒，也返回 1。计算先做整数除法再检查余数，避免浮点误差和 duration 加法溢出。它是建议等待，不承诺到期时一定有名额。[Retry-After 定义](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Retry-After)

服务器发出响应头，并不等于跨域页面脚本能读取所有头。因此 CORS 的普通允许响应现在暴露 X-Request-ID 与 Retry-After。未知来源仍没有放行头，预检的允许方法/请求头策略也保持原样。[Expose-Headers 说明](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Access-Control-Expose-Headers)

### 本次学习概念

用户 ID 来自上一阶段验证通过的内部身份，安装 ID 来自客户端持久保存的 UUID。它们解决不同问题：用户 ID 确定数据属于谁，安装 ID 确定这个用户的哪次客户端安装。数据库唯一键是两者组合，因此两个用户可以在同一安装标识下各自拥有设备记录，查询时不能省掉用户条件。

查询核心如下：

~~~go
store.database.WithContext(queryContext).
    Select("id", "user_id", "installation_id", "name", "platform", "revoked_at").
    Where("user_id = ? AND installation_id = ?", userID, installationID).
    Take(&record)
~~~

这两个问号都是参数绑定。即使有人绕开 DTO 直接传入空字符串或包含 SQL 片段的安装 ID，也只会按该值查找，不能去掉用户范围或改写条件。userID=0 在方法入口拒绝，避免把没有验证过的默认身份继续交给数据库查询。

数据库 NULL 与某个具体时间不同。revoked_at=NULL 表示当前没有撤销时间，所以 Go 使用 *time.Time：nil 对应 NULL，非 nil 才有实际时间。若直接用 time.Time，容易把“没有时间”与零值时间混为一谈。[GORM 可空字段](https://gorm.io/docs/models.html)

这里没有用 gorm.DeletedAt，因为设备撤销并不是把记录从普通查询里隐藏。即使已经撤销，也需要查到原记录，供后续业务判断。Repository 返回事实；本轮既不恢复设备，也不决定它是否允许重新登录。

models.LoginDevice 与 domain.LoginDevice 字段相似，但职责不同：前者声明数据库列和只读权限，后者给业务层使用。查询只取六列，不把系统版本、应用版本、更新时间等本轮不用的字段一并引入；后续功能需要时再扩展相应模型。

错误同样分两层：ErrDeviceNotFound 只表示该用户下没有匹配设备；数据库连接已关闭、读取失败或超时都属于真正的故障。后续 Service 可以在未找到时考虑创建设备，但不能把数据库断开误当成“新设备”再继续写入。

## 第 026 步——建立登录写入的用户事务入口

### 编码前的小方案

新增 Store.WithLoginUserTransaction(ctx, userID, action func(context.Context, *Store) error) error。输入是已验证的非零用户 ID、上下文和事务回调；先开启事务，用 users 主键锁定读取 id/status，只有 ACTIVE 才调用回调，回调同时拿到事务子上下文和绑定该事务的 Store。成功提交后返回 nil，其他路径返回错误或继续传播原 panic。

- 这是登录阶段的专用入口，尚无登录会话，因此只复查账号状态，不冒充后续需要 actor/session 检查的通用 WithUserTransaction。认证写入继续遵守 users → user_devices → auth_sessions 顺序；本轮回调仅在测试中演示，不创建生产设备/会话或新路由。

- 整个事务派生最多 5 秒上下文，包括开始、等锁、查询、回调数据库操作和提交前检查；调用方更短期限仍生效。回调必须合作使用传入事务上下文及 Store，不能用外层上下文覆盖事务内查询期限，不执行 bcrypt/存储网络操作、不在事务外启动异步任务。对不响应取消的普通回调代码不承诺强制中断。
- 使用既有 models.LoginAccount 只读投影，但只 Select id/status，不读摘要；Where("id = ?", userID) + FOR UPDATE + Take。未命中返回 ErrAccountNotFound，DISABLED 返回 ErrAccountDisabled，未知状态或异常 ID 返回 ErrInvalidAccountData，故障保留原因，拒绝路径不执行回调。
- 手动 Begin/Commit，并用 defer 对尚未成功提交的事务尝试 Rollback。回调错误和正常返回路径的回滚故障通过 errors.Join 保留错误链；sql.ErrTxDone 视为事务已经结束而忽略。panic 时也尝试回滚并保留原 panic，不用清理错误替换它。
- 提交错误作为内部故障返回，不重试、不声称提交故障一定意味着未写入；网络故障下提交结果可能不确定。调用方必须以外层返回成功为准，不能仅因回调执行或赋值就宣告登录成功。事务 Store 不得被保存到回调外使用。

      ├─ 未找到/禁用/未知状态/查询故障 → 返回错误并回滚
      └─ ACTIVE → action(transactionContext, transactionStore)
                   ├─ 返回错误/panic → 回滚，保留原因或原 panic
                   └─ nil → 再检查上下文 → Commit
                             ├─ 提交失败 → 返回错误，不重试回调
                             └─ 提交成功 → 返回 nil
~~~

### 本次学习概念

前面的凭证和设备查询得到的是某一时刻的结果。查询结束后，另一个操作可能禁用账号，所以不能仅拿旧的 ACTIVE 状态继续创建设备和会话。本入口在写入事务内重新读取用户状态，并先锁住对应用户行。配合其他写操作遵循相同用户锁顺序，便能把同一账号的重要写入排好顺序。[MySQL 锁定读取](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)

事务可以理解为一组数据库操作的共同边界：回调返回 nil 才尝试提交，返回错误则撤销本次事务中的写入。但这个边界只覆盖同一数据库事务内的操作，不能回滚文件、网络请求或外部服务副作用，因此回调不能夹带 bcrypt 计算、MinIO 调用或不受控制的异步工作。

回调收到的 transactionStore 和外面的 store 具有相同方法，但底层连接不同：前者绑定 sql.Tx，后者连接共享池。进入回调后必须使用前者，才能让设备查询和后续写入属于同一事务。事务结束后不再保存或继续使用它。[GORM 事务中的句柄使用](https://gorm.io/docs/transactions.html)

回调还会收到 transactionContext，后续 Repository 调用要传它，而不是重新使用外层请求上下文。这样查询自己的短期限会继续受事务总期限约束。这个设计仍要求普通回调代码合作响应取消，不会用额外 goroutine 假装中断不响应上下文的代码。

`FOR UPDATE` 是锁定读取，不是普通快照查询：同一用户的另一个遵守相同规则的事务需要等待这把行锁；取得锁后重新检查状态。不同用户使用不同主键行锁。本轮真实测试特意让先拿到锁的事务提交 DISABLED，检查等待者不会按旧状态进入回调。

本方法使用 defer 登记回滚，正常错误返回、提前结束和 panic 都能经过清理。命名返回值 err 允许清理时用 errors.Join 保留“业务回调失败”和“回滚失败”两条错误链；panic 则继续沿原调用栈传播，不替换原载荷。sql.ErrTxDone 表示事务已经由提交或取消处理结束，不作为新的回滚故障重复报告。

提交失败可能是网络中断，调用方不能简单断言数据一定没提交，也不能自动重跑回调。本入口不自动重试；后续业务的幂等和可查询结果需要在对应流程里设计。只有外层方法返回 nil 时，调用方才能把这次事务当作已确认成功，不能仅凭回调曾经执行过判断。

### 调用示例与验证

未来登录业务使用下面的形式。回调中的设备查询沿用第 025 步；本轮尚不写入生产设备或会话：

~~~go
err := store.WithLoginUserTransaction(ctx, verifiedAccount.ID,
    func(txContext context.Context, transactionStore *repository.Store) error {
        // 1. 使用事务上下文和事务 Store 查询设备。
        device, err := transactionStore.FindLoginDeviceByInstallation(
            txContext, verifiedAccount.ID, input.InstallationID)
        // 2. 后续小步再根据 device/err 决定创建或复用。
        // 回调返回 nil 允许提交；返回错误则回滚。
        _ = device
        return err
    })
// 3. 检查外层 err，提交确认成功后才继续处理登录结果。
~~~

上例只是展示事务调用结构；未来设备不存在时，业务层应处理 ErrDeviceNotFound 后再创建设备，不能直接将它等同于登录失败。
