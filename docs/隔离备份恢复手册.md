# CloudNest 阶段 1 隔离备份恢复手册

本手册用于在两套独立的本机测试环境之间演练备份与恢复。输入是停止写入的合成数据和本轮记录的源端标识，产物是 MySQL 导出、目录与对象清单、对象正文、完整性校验记录，以及全新环境中的恢复结果。本步交付操作顺序和验收标准，实际演练另行记录。

B5 样本在数据库和对象映射核对后、目标后端启动前，须执行[第 4.1 节的离线同步换代](#41-b5-离线同步换代)。协议和验收范围见 [B5 第 16 节](B5-同步与历史协议.md#16-备份恢复后的同步代次重置)。

## 1. 准备源端、目标端和样本

1. 为源端和目标端各创建一套专用 MySQL、MinIO 和回环服务。参考仓库隔离联测的固定镜像、临时存储和动态回环端口。记录 Docker 容器 ID、回环地址、库名、桶名和服务端口。两套环境使用独立凭据，MinIO 桶开启版本控制。将目录、对象和数据库产物保存到与两端存储分离的位置。
2. 核对每个地址和标识确实属于本次演练。源端和目标端禁止使用现有开发库、已有桶、已有 Docker 卷、默认服务端口或真实账号。目标库创建为空库，目标桶没有对象及历史版本。后端启动参数中同时核对 `CLOUDNEST_S3_ENDPOINT` 和 `CLOUDNEST_S3_PUBLIC_ENDPOINT`，签名下载也须指向隔离实例。
3. 在源端执行仓库现有迁移，使用合成账号经正式接口生成样本。准备一个活动文件（4 B）、回收目录中的一个文件（6 B，子项可仍为 `ACTIVE`）、一个活动空文件（0 B），以及一个已创建但未发送正文的上传任务（预占 3 B）。使用固定合成字节并记录 SHA-256。按条目计的源端预期是已用 10 B、预占 3 B。回收目录应为近期回收项，避免演练期间触发 30 天保留规则。

所用入口见 [隔离测试夹具](../cmd/server/web_upload_content_integration_test.go) 和 [迁移说明](../migrations/README.md)。

可从仓库根目录运行源端基线联测。联测新建并清理专用容器、库和桶，日志提供本轮对象版本、正文摘要和配额。后续备份时重新生成同类样本，以当轮输出作为比对基线。

~~~powershell
$env:CLOUDNEST_BACKUP_SOURCE_TEST = '1'
$env:GIN_MODE = 'release'
go test -count=1 -v ./cmd/server -run '^TestServerBackupSourceIntegration$'
~~~

## 2. 停止写入并取得同一时点的备份

1. 暂停源端客户端和任何写入程序。优雅停止本次源端后端并等待进程退出，确认 HTTP 和上传校验、过期、取消、永久清理、对象回收及回收站到期标记任务均已结束。MySQL 和 MinIO 保持可访问供导出。核对不存在其他客户端、管理脚本或桶生命周期规则在写入或删除。记录停写开始及确认完成的 UTC 时间。
2. 检查快照中是否还存在可能在恢复时被 worker 立即执行的工作。首轮样本只保留一项无正文、无有效执行租约的 `SINGLE/UPLOADING` 任务，并记录截止时间。确认快照内没有其他未终结上传、`PURGING` 条目、`DELETING` 对象或演练期间到期的回收站和对象回收候选。遇到这些状态，停在快照检查并明确收尾方式，然后重新生成同一时点的记录。
3. 导出同一业务库的八张表及 `schema_migrations`，带结构和数据。对象清单、目录和配额基线都在该停写窗口内取得。记录代码提交、迁移版本及摘要、MySQL 和 MinIO 镜像标识，并校验数据库导出文件的 SHA-256。

使用源 MySQL 容器自带的客户端。先将 `$sourceMysql`、`$sourceDb` 和 `$backupDir` 指向已核对的本轮容器 ID、库名和全新产物目录。每条命令成功后再继续，密码在提示时输入。

~~~powershell
docker exec -it $sourceMysql mysqldump --user=root -p --single-transaction --hex-blob --no-tablespaces --set-gtid-purged=OFF --skip-add-drop-table --result-file=/tmp/cloudnest-backup.sql $sourceDb
docker cp "${sourceMysql}:/tmp/cloudnest-backup.sql" (Join-Path $backupDir 'database.sql')
Get-FileHash -Algorithm SHA256 -LiteralPath (Join-Path $backupDir 'database.sql')
~~~

导出按库名取表，省略 `--databases`，便于导入另一个名称的空库。`--hex-blob` 以十六进制保存二进制列，`--result-file` 直接生成备份文件。命令失败时，生成的文件也可能不完整。 [MySQL 8.4 导出说明](https://dev.mysql.com/doc/refman/8.4/en/mysqldump.html)

源端导出联测复用第 1 节夹具，用相同环境变量运行 `go test -count=1 -v ./cmd/server -run '^TestServerBackupSourceDumpIntegration$'`。联测确认 HTTP 和六个 worker 退出，记录迁移与镜像信息，核对容器内外 SHA-256 和逐表行数，结束后清理临时 SQL 文件和专用资源。 [复验记录](开发学习记录.md#第-537-步验证隔离源端停写与-mysql-快照导出)

快照窗口的实现依据见 [后端启动与关停](../cmd/server/main.go)。

## 3. 核对目录引用和对象正文

在已核对的源测试库运行以下只读查询。`LEFT JOIN` 保留关联缺失的条目，方便发现错误。子文件自身为 `ACTIVE`、父目录已回收时，同样可以进入清单。

~~~sql
SELECT e.user_id, e.id AS entry_id, e.parent_id, e.name, e.status AS entry_status,
       e.object_id, e.file_size AS entry_bytes,
       o.status AS object_status, o.provider, o.bucket, o.object_key,
       o.storage_version_id, o.file_size AS object_bytes,
       LOWER(HEX(o.verified_sha256)) AS sha256
FROM file_entries AS e
LEFT JOIN stored_objects AS o ON o.owner_user_id = e.user_id AND o.id = e.object_id
WHERE e.entry_type = 'FILE' AND e.status <> 'PURGED'
ORDER BY e.user_id, e.id;
~~~

1. 保存目录树基线和上述文件引用，逐项核对对象为 `READY`、位置齐全、逻辑字节数相等且 SHA-256 存在。单独盘点未被文件引用的对象记录和未终结任务。首轮样本中的暂存对象只保留元数据，应确认它从未写入正文。发现无法解释的对象版本或缺失引用时停止。
2. 按 `stored_objects.id` 去重为物理对象清单。同一对象可被多个目录项引用，备份正文只取一次。清单记录归属、对象 ID、源 `provider`、桶、键、可空 `storage_version_id`、字节数、SHA-256 和备份正文相对路径。对象正文文件名可用对象 ID，避免使用用户文件名或对象键拼出本机路径。
3. 用隔离 MinIO 客户端按清单从源桶读取每个对象。保存了版本 ID 时按该版本下载，保留 `NULL` 与字符串 `null` 的区别。对下载结果重新计算字节数和 SHA-256，逐项匹配清单。对数据库文件、清单及每份正文记录校验值。内容和清单都可读取且校验一致后才认定备份包完整，记录停写结束时间。若仍需使用源端，按原有隔离参数恢复运行。
4. 备份包包含账号及会话摘要和文件内容，保存在隔离产物目录。凭据和本机配置单独保护，备份包和凭据均禁止放入 Git。

清单联测使用第 1 节环境变量，运行 `go test -count=1 -v ./cmd/server -run '^TestServerBackupSourceManifestIntegration$'`。同一次停写后导出 SQL 并生成 `manifest.json`，以 `database_sha256` 对应当轮快照，以 `directories`、`file_references` 和 `objects` 记录目录、文件引用与物理定位。测试读回 JSON，并只读列举 MinIO 版本核对清单。 [复验记录](开发学习记录.md#第-538-步生成隔离源端目录与对象版本清单)

正文联测使用相同环境变量，运行 `go test -count=1 -v ./cmd/server -run '^TestServerBackupSourcePayloadIntegration$'`。在同一个临时目录生成 `database.sql`、`manifest.json` 与 `objects/`。正式命名之前核对来源版本、字节数及 SHA-256，写入完成后再从磁盘独立读回复核。 [复验记录](开发学习记录.md#第-539-步按版本保存隔离源端备份正文)

版本及对象位置校验见 [存储读取规则](../internal/server/storage/object_read.go) 和 [下载前的对象核对](../internal/server/storage/download_object.go)。

## 4. 恢复到全新隔离环境

1. 保持目标后端关闭。复核目标容器 ID、库名、桶和端口，确认它们与源端分离。校验备份文件及清单，确认目标库为同版本 MySQL 上的空库。导入备份中的结构、数据和迁移记录。

   先将 `$targetMysql` 和 `$targetDb` 指向已核对的目标容器 ID 和空库，再执行以下命令。导入出错时保留证据并停止，后续复验使用新的空目标库。

   ~~~powershell
   docker cp (Join-Path $backupDir 'database.sql') "${targetMysql}:/tmp/cloudnest-restore.sql"
   docker exec -it $targetMysql mysql --user=root -p --database=$targetDb --execute='source /tmp/cloudnest-restore.sql'
   ~~~

   [MySQL 8.4 恢复 SQL 备份说明](https://dev.mysql.com/doc/refman/8.4/en/reloading-sql-format-dumps.html)

2. 记录导入后各表的行数，核对 `schema_migrations` 里的版本、摘要及 `dirty=false`，对照源端清单检查目录父子关系、回收时间、账号和配额。使用当前应用的同版本程序验收。

   SQL 导入联测使用第 1 节环境变量，运行 `go test -count=1 -v ./cmd/server -run '^TestServerBackupTargetSQLIntegration$'`。测试起两套独占 MySQL，先检查目标空库与容器内外文件摘要，再对照源端清单核对导入结果。目标端只运行 MySQL。 [复验记录](开发学习记录.md#第-540-步导入并核对隔离目标数据库)

3. 将清单中的正文逐对象写入目标桶，沿用不可变对象键。保存实际写入结果的目标桶、键、版本 ID 和 ETag。按目标版本读回并重新计算字节数与 SHA-256。目标版本来自本次写入结果，源版本仍保留在清单里用于追溯。

   对象恢复联测使用第 1 节环境变量，运行 `go test -count=1 -v ./cmd/server -run '^TestServerBackupTargetObjectsIntegration$'`。测试在独立 MinIO 容器的新版本化桶恢复并读回正文，记录 `object-version-map.json`，以清单 SHA-256 绑定本轮备份。 [复验记录](开发学习记录.md#第-541-步恢复隔离目标桶对象并记录版本映射)

4. 只在目标库事务内按对象 ID、归属和预期源定位更新已复制对象的存储定位及 ETag。实际受影响的记录与目标映射清单逐项核对，失败则回滚。演练使用当前 `local_minio` provider 和显式目标桶。对于首轮样本中从未写正文的暂存记录，只将其定位对齐到已核验的目标桶，保留无版本语义，再通过目标环境的取消流程结算。无法确认来源的记录保持隔离并停止启动。保持文件大小、验证摘要、对象引用和配额结算含义。

   已发布对象定位联测使用第 1 节环境变量，运行 `go test -count=1 -v ./cmd/server -run '^TestServerBackupTargetRemapIntegration$'`。联测用同轮已保存的清单与映射更新三条 `READY` 记录，并验证一条源版本失配时整批回滚。 [复验记录](开发学习记录.md#第-542-步按版本映射更新隔离目标库的已发布对象)

   暂存桶对齐联测使用相同环境变量，运行 `go test -count=1 -v ./cmd/server -run '^TestServerBackupTargetStagingIntegration$'`。先用版本列表确认目标暂存键没有正文版本或删除标记，再按原定位、空内容元数据和未发送任务状态条件更新桶名。 [复验记录](开发学习记录.md#第-543-步对齐隔离目标库未发送任务的暂存桶)

5. B5 样本先完成[第 4.1 节](#41-b5-离线同步换代)的换代与复核。在所有映射及基线核对通过后，用目标的连接参数、目标桶和独立 JWT 密钥启动隔离后端。用新的浏览器会话登录合成账号。检查该未完成任务归属、状态、到期时间和租约；如果仍可取消，走已有取消接口并等待 `CANCELLED`。如果已到期，等待既有过期流程交付 `EXPIRED`。核对任务及用户预占确实结算、任务没有发布文件，再开始后续读回验收。

   目标端取消联测使用第 1 节环境变量，运行 `go test -count=1 -v ./cmd/server -run '^TestServerBackupTargetCancelIntegration$'`。通过正式登录、取消和任务查询接口核对恢复后的未发送任务，等待真实 worker 回收预占，复核已发布版本。 [复验记录](开发学习记录.md#第-544-步取消恢复后未发送任务并返还预占)

   活动文件下载联测使用相同环境变量，运行 `go test -count=1 -v ./cmd/server -run '^TestServerBackupTargetDownloadIntegration$'`。测试从目标根目录申请实际签名链接，核对隔离目标桶和版本，再读回 4 B 活动文件与 0 B 空文件。 [复验记录](开发学习记录.md#第-545-步验收恢复后活动文件的签名下载)

   回收目录恢复联测使用相同环境变量，运行 `go test -count=1 -v ./cmd/server -run '^TestServerBackupTargetRestoreIntegration$'`。测试比对回收站原路径和时间，确认恢复前不能浏览，使用回收站返回的版本提交恢复。恢复到原位置后，签名下载 6 B 子文件并按备份清单核对摘要、目标版本和配额。 [复验记录](开发学习记录.md#第-546-步验收恢复后回收目录子文件的签名下载)

### 4.1 B5 离线同步换代

**核对目标。** B5 演练使用当前迁移的全量数据库备份，包含 `change_events`、`sync_devices` 与 `file_versions`。完成第 4 节步骤 1～4 后，核对当前和历史正文的目标版本映射、配额、账号累计序号和保留日志范围。目标 HTTP、后台任务和其他业务写入程序保持停止。通过已核对的目标容器读取并记录 MySQL 实例 UUID 和库名，以容器的实际回环映射填写 `$targetDbAddress`（例如 `127.0.0.1:54123`）。把身份、备份摘要与本次恢复产物目录对应写入演练记录。

~~~powershell
docker port $targetMysql 3306/tcp
docker exec -it $targetMysql mysql --user=root -p --database=$targetDb --execute='SELECT @@GLOBAL.server_uuid AS server_uuid, DATABASE() AS database_name'
~~~

**预检。** 在仓库根目录开启用于本次恢复的 PowerShell。将 `$targetServerUUID` 设为刚记录的 UUID，`$restoreDir` 设为本次恢复已存在的产物目录，文件系统须支持同目录硬链接。输入隔离目标的数据库凭据，预检通过后再执行换代。预检只读核对实例、库名及迁移记录。

~~~powershell
$rosterPath = Join-Path $restoreDir 'original-sync-roster.json'
$env:CLOUDNEST_RESTORE_DB_USER = Read-Host '目标 MySQL 用户名'
$restorePassword = Read-Host '目标 MySQL 密码' -AsSecureString
$env:CLOUDNEST_RESTORE_DB_PASSWORD = [System.Net.NetworkCredential]::new('', $restorePassword).Password
$restorePassword.Dispose()
$targetArgs = @('-db-address', $targetDbAddress, '-database', $targetDb,
    '-server-uuid', $targetServerUUID, '-roster', $rosterPath)
go run ./cmd/restore-sync check @targetArgs -mode initial
if ($LASTEXITCODE -ne 0) { throw '恢复目标预检失败，保持停服' }
~~~

**首次执行。** 使用本次恢复的全新清单路径。命令先保存导入时的全部同步记录，再分批换代并重新读回核对。有同名清单时会停止。首次运行后，只要原清单已经生成，就记录其 SHA-256，包括命令中途失败的情况。

~~~powershell
if (Test-Path -LiteralPath $rosterPath) { throw '首次清单路径已存在，请核对本次恢复记录' }
go run ./cmd/restore-sync reset @targetArgs -mode initial
$resetExitCode = $LASTEXITCODE
if (Test-Path -LiteralPath $rosterPath -PathType Leaf) {
    Get-FileHash -Algorithm SHA256 -LiteralPath $rosterPath
}
if ($resetExitCode -ne 0) { throw '同步换代未完成，保持停服并检查已提交进度' }
~~~

**故障重跑。** 保持目标停服。保留日志及原清单，读取实际持久化状态，查明失败原因。若首次已生成清单，重新核对同一个备份、目标标识及清单 SHA-256。按预检段重新准备 `$targetArgs` 和凭据，将 `$originalRosterSHA256` 设置为先前记录的摘要，再用 `resume` 重跑。已成功提交的设备可以再次换代，最后仍与首次记录的原代次比对。原清单缺失且无法确认从未写入时，停在原样本，使用已核验的备份重新建立新的隔离目标再演练。确认尚未生成清单且没有提交时，可排除故障后重新首次执行。

~~~powershell
if ((Get-FileHash -Algorithm SHA256 -LiteralPath $rosterPath -ErrorAction Stop).Hash -ne $originalRosterSHA256) {
    throw '原始清单摘要不符，保持停服'
}
go run ./cmd/restore-sync check @targetArgs -mode resume
if ($LASTEXITCODE -ne 0) { throw '恢复目标预检失败，保持停服' }
go run ./cmd/restore-sync reset @targetArgs -mode resume
if ($LASTEXITCODE -ne 0) { throw '同步换代未完成，保持停服' }
~~~

**复核后启动。** 记录命令退出状态、确认提交数和全量复核数。两项计数均须等于原清单条数，空清单时均为 0。换代前后在目标库各执行以下只读查询，按账号与设备比对。换代后的每条记录都应为 `RESET_REQUIRED`，`ack_sequence=0`，当前代次有效且与原清单不同。同步活动时间、创建时间、账号累计序号、保留日志行数及范围均与换代前一致。

~~~sql
SELECT user_id, device_id, status, LOWER(HEX(cursor_generation)) AS generation,
       ack_sequence, last_seen_at, created_at
FROM sync_devices
ORDER BY device_id;

SELECT u.id AS user_id, u.change_seq, COUNT(e.`sequence`) AS retained_events,
       MIN(e.`sequence`) AS first_retained, MAX(e.`sequence`) AS last_retained
FROM users AS u
LEFT JOIN change_events AS e ON e.user_id = u.id
GROUP BY u.id, u.change_seq
ORDER BY u.id;
~~~

目录、当前及历史对象引用和配额也须与换代前一致，全部符合才按第 4 节步骤 5 启动目标。本次操作结束或故障停在当前步骤时，清除当前 PowerShell 的专用凭据。

~~~powershell
Remove-Item Env:CLOUDNEST_RESTORE_DB_USER,Env:CLOUDNEST_RESTORE_DB_PASSWORD
~~~

**启动后验收。** 同序号再次出现的复验需要在停写备份前记录同一合成设备的基线与游标，备份后在隔离源端生成新的变更与旧代次游标。启动目标后写入不同内容，使该序号再次出现。仅为本项隔离复验，两端使用同一把合成签名密钥，以便有效的同设备会话复验可验签的旧凭据。旧游标拉取、确认和未到期的旧快照续页、基线确认均须返回 `410 CURSOR_EXPIRED`。客户端保留本地未提交内容，使用新幂等键创建快照，保存完整基线后确认，再用新游标续读。普通重启后复核新基线仍可使用。记录每个响应状态及实际序号。 [验收矩阵](B5-同步与历史协议.md#163-隔离验收)

## 5. 验收和退出条件

| 检查项 | 通过依据 |
|---|---|
| 登录和目录 | 合成账号可登录，根目录、子目录、原父级关系、活动条目与基线一致 |
| 回收站 | 近期回收目录、原位置及回收时间一致。恢复后可按正式入口下载其子文件，已用仍为 10 B |
| 内容 | 通过目标服务签发链接下载活动文件、空文件和已恢复子文件，逐项匹配原字节数和 SHA-256 |
| 配额和任务 | 导入后已用 10 B、预占 3 B。取消或到期收尾后已用仍为 10 B、预占为 0 B，目标任务没有发布目录项 |
| 演练记录 | 有源/目标标识、备份包摘要、对象版本映射、按阶段 UTC 计时及检查结果。任何异常对应明确的停点 |

配额从数据库重算时，分别汇总未永久清理的文件逻辑大小和任务预占。回收目录下的文件继续计入已用。多个目录项共享一个对象时，逻辑大小按目录项累加。

~~~sql
SELECT u.id, u.storage_quota, u.used_storage, u.reserved_storage,
       COALESCE((SELECT SUM(e.file_size) FROM file_entries AS e
                 WHERE e.user_id = u.id AND e.entry_type = 'FILE' AND e.status <> 'PURGED'), 0) AS expected_used,
       COALESCE((SELECT SUM(t.reserved_bytes) FROM upload_tasks AS t
                 WHERE t.user_id = u.id), 0) AS expected_reserved
FROM users AS u
ORDER BY u.id;
~~~

记录 `used_storage = expected_used`、`reserved_storage = expected_reserved` 和两者之和不超过 `storage_quota` 的检查结果。摘要、版本、迁移、目录或配额有一项不符即停止验收，保留本次产物及诊断记录。清理只按本次台账处理已经确认归属的临时资源。

原方案以每天备份一次、保留最近 7 份每日备份为初始目标，恢复点目标为 24 小时内，恢复耗时目标为 4 小时。演练记录实际停写和恢复时长，结合备份时间评估目标。保留策略和原始要求见 [整体技术方案](../云盘%20SaaS%20项目技术方案书（混合架构版）.md#112-备份目标与执行)。
